## 들어가며

이 책은 흩어져 있던 학습 노트를 **"구조를 설계하고, 운영 중에 바꾸는 엔지니어"**라는 하나의 목적으로 다시 묶은 것이다.
회사들이 모놀리스를 쪼개고, 다시 합치고, 클라우드에서 나오기도 하는 이유는 결국 **트레이드오프**다. 그 판단을 내리려면 먼저 컴퓨터가 일하는 방식, 데이터가 어긋나는 방식, 경계를 긋는 방식을 알아야 한다.

**책의 흐름**
- **1부 컴퓨터가 일하는 방식** — 추상화, 메모리, 동시성, 자료구조. 모든 비용의 바닥.
- **2부 데이터와 일관성** — 트랜잭션, 캐시, 분산 정합성, 통신, 성능. 시스템이 여러 개가 될 때 생기는 문제.
- **3부 경계를 긋는 법** — 설계의 출발점, 모듈성, 콘웨이 법칙, 배치(온프레미스·클라우드).
- **4부 운영 중인 구조 바꾸기** — 실제 회사들의 전환 사례와, 바꾼 구조를 CI로 지키는 법.
- **5부 AI 시대의 검증** — 구현이 싸지면서 병목이 검증으로 옮겨간 이야기, 테스트와 품질 게이트.
- **부록** — 언어·도구, 수학, AI·머신러닝, 그래픽스·Unity, 면접·코딩테스트.

## 트레이드오프를 읽는 법 — 지표는 '수단'이지 절대 기준이 아니다

> 핵심 태도: 기술 선택은 "똑똑해 보이는 X/Y 그래프"가 아니다.
> **"지금 풀려는 문제가 무엇인가"** 가 먼저고, 지표·기술은 그걸 푸는 **수단**일 뿐이다.
> 무조건적인 정답은 없다.

### 1. 모든 선택에는 '축'이 있다 — 무엇을 얻고 무엇을 잃나

거의 모든 기술 결정은 **하나를 얻으면 다른 하나를 내주는** 구조다.
"좋다/나쁘다"가 아니라 **"무엇을 무엇과 바꾸나"** 로 봐야 한다.

| 선택 | 얻는 것 | 내주는 것 (대가) |
|------|---------|-----------------|
| 인덱스 추가 | 읽기(검색) 속도 | 쓰기 속도·저장공간·캐시 |
| 캐싱 | 응답 속도 | 정합성(stale)·무효화 복잡도 |
| 정규화 | 쓰기 속도·정합성 | 읽기 속도(JOIN) |
| 비정규화 | 읽기 속도 | 쓰기 속도·중복 동기화 |
| 수평 확장 | 처리량·가용성 | 지연·복잡도 |
| ORM | 생산성·이식성 | 세밀한 성능 제어 |
| 비동기(async) | I/O 대기 동안 처리량 | 오버헤드·코드 복잡도 |
| 서버리스 | 운영 부담↓·스파이크 대응 | 고정 고트래픽 단가↑ |
| UUID PK | 분산 생성·충돌 회피 | 인덱스 단편화·insert 저하 |
| 마이크로서비스 | 독립 배포·장애 격리 | 운영·네트워크·비용 복잡도 |
| 추상화 레이어 추가 | 유연성·교체 용이 | 인지 비용·간접성·디버깅 난이도 |

→ 이 표의 핵심은 값이 아니라 **사고법**: 새 기술을 볼 때 "이건 무슨 축을 바꾸지?"를 묻는다.

### 2. 왜 '인덱스'를 예로 보면 좋은가

인덱스는 트레이드오프가 **눈에 보이게** 드러나는 교과서적 예다:
- **얻음**: `WHERE`/`JOIN`/정렬 조회가 O(n)→O(log n)으로.
- **내줌**: INSERT/UPDATE/DELETE마다 인덱스도 갱신 → **쓰기가 인덱스 개수만큼 느려짐**.
  저장공간↑, 인덱스 페이지가 캐시(RAM)를 점유 → 캐시 압박↑.
- **무엇이 바뀌면 결정이 바뀌나**: **읽기:쓰기 비율**. 읽기 위주면 인덱스 이득,
  쓰기 폭주면 인덱스가 독. → "인덱스는 좋다"가 아니라 **"이 워크로드에 좋은가"**.

이 한 예시만 제대로 이해하면, 다른 모든 트레이드오프도 같은 틀로 읽힌다.

### 3. 그래서 무엇으로 검증하나 — 지표(metric)

트레이드오프를 "감"이 아니라 **숫자로 확인**하려면 지표가 필요하다. 단:

#### 지표는 '문제 해결'을 확인하는 수단이지, 그 자체가 목표가 아니다
- 인덱스를 넣었으면 → **조회 p95 지연**이 줄었나? 동시에 **쓰기 처리량(TPS)**은 안 망가졌나?
- 캐시를 넣었으면 → **DB 부하/응답시간**이 줄었나? **stale로 인한 오류**는 안 늘었나?
- 즉 지표는 **"얻은 축"과 "내준 축"을 같이** 본다. 한쪽만 보면 속는다.

#### 똑똑해 보이는 지표의 함정 — Goodhart's law
> "측정값이 목표가 되는 순간, 그것은 좋은 측정값이기를 멈춘다." (Goodhart's law)

지표를 **목표로 삼으면 사람들은 지표를 game**한다 (소련 못 공장: 개수 목표→쓸모없는 작은 못
양산, 무게 목표→거대한 못). 엔지니어링에서도 응답시간 평균만 쫓다 **꼬리지연(p99)**을 놓치거나,
커버리지 숫자만 채우려 의미 없는 테스트를 쓴다.
출처: [Goodhart's law (Wikipedia)](https://en.wikipedia.org/wiki/Goodhart%27s_law),
[엔지니어링 적용](https://vikky.dev/goodharts-law)

#### 무엇을 재나 — 지표 예시 (나열)
"빠르다/느리다" 같은 막연함 대신, 목적에 맞는 구체 지표를 고른다:
- **지연(latency)**: 평균이 아니라 **p95/p99(꼬리지연)** 를 본다. 평균은 소수의 느린 요청을 숨긴다.
- **처리량(throughput)**: 초당 요청/트랜잭션(RPS/TPS). 지연과 함께 봐야(둘은 트레이드오프).
- **자원**: CPU·메모리 사용률, **메모리 여유**(스왑 직전인지), 커넥션 풀 점유.
- **오류율**: 5xx 비율, 타임아웃, **stale/정합성 오류**(캐시 도입 시 반드시).
- **비용**: 요청당 단가, 월 청구서 (서버리스 vs 서버 판단).
- **체감**: 사용자 입장의 완료 시간(여러 왕복 합산), 첫 응답까지 시간(TTFB).
- **개발 비용**: 구현·유지보수 시간 (성능만이 지표가 아니다).

> 핵심: **"얻은 축"과 "내준 축"을 한 쌍으로** 잰다. 조회를 빠르게 했으면 쓰기·메모리도 같이 확인.

#### 측정 먼저 (Knuth)
> "조기 최적화는 만악의 근원" = **측정 전에 추측으로 최적화하지 말라**.
직관은 거의 빗나간다 → 프로파일링으로 진짜 병목(3%)을 찾고 거기만.
출처: [Knuth 원문 맥락](https://probablydance.com/2025/06/19/revisiting-knuths-premature-optimization-paper/)

### 4. 한 장 요약 — 판단 순서

```
1. 무슨 문제? — "느리다"가 아니라 "무엇이, 얼마나, 누구에게 문제인가" (목적 정의)
2. 무슨 축?   — 이 선택이 무엇을 얻고 무엇을 내주나 (트레이드오프 명시)
3. 무슨 지표? — 목적을 달성했는지 + 대가가 감당 가능한지 둘 다 측정
4. 측정 먼저  — 추측 금지. 적용 전/후 비교.
5. 지표를 목표로 삼지 말 것 — 지표는 문제 해결의 증거일 뿐 (Goodhart)
```

> 결국 중요한 건 **"이 문제를 풀기 위함"**. 기술도 지표도 거기에 종속된다.
> "무조건 이게 정답"은 없다 — 이 레포의 일관된 태도.

## 추론 기법 — LLM 시대에 사고력을 잃지 않기

> 왜 이 문서가 있나: LLM이 **근거 찾기**를 쉽게 해주는 대신, 스스로 생각하는 노력이 줄어
> "생각하는 법"을 잊기 쉽다. 판단(어떤 원칙을 언제 적용할지)은 결국 사람의 추론이다.
> 그 추론을 **의식적으로 연습**하기 위한 노트.

### 경고 — AI는 사고를 '검증'으로 옮긴다 (연구 근거)

Microsoft의 지식노동자 319명 설문(CHI 2025):
- **AI를 더 신뢰할수록 비판적 사고를 덜 한다.** 반대로 자기 확신이 높을수록 더 한다.
- 응답자 다수가 GenAI 사용 시 인지 노력이 **줄었다**고 보고
  (지식수집 72%, 이해 79%, 분석 72%, 종합 76%가 "노력 덜 듦").
- 사고의 성격이 **정보 검증·응답 통합·작업 관리(stewardship)** 로 이동.
- 출처: [The Impact of GenAI on Critical Thinking (MS, CHI 2025)](https://www.microsoft.com/en-us/research/publication/the-impact-of-generative-ai-on-critical-thinking-self-reported-reductions-in-cognitive-effort-and-confidence-effects-from-a-survey-of-knowledge-workers/)

→ 결론: LLM 시대엔 **"답을 만드는 힘"보다 "검증·판단하는 힘"이 더 중요**해진다.
   그 힘은 추론을 직접 굴려야 유지된다 (안 쓰면 퇴화). 카파시식 "직접 해보기"와 같은 맥락.

### 추론 3종 (도구상자)

| 종류 | 방향 | 예 | 한계 |
|------|------|-----|------|
| **연역(Deductive)** | 일반 원칙 → 구체 결론 | "쓰기 잦으면 인덱스 손해 / 이건 쓰기 잦음 → 인덱스 줄여라" | 전제가 틀리면 결론도 틀림 |
| **귀납(Inductive)** | 구체 관찰 → 일반화 | "이 4개 회사가 모놀리스로 성공 → 중소엔 모놀리스가 낫다" | 반례 하나로 무너짐(잠정적) |
| **가추(Abductive)** | 증상 → 최선의 가설 | "응답이 느리다 → 아마 N+1 쿼리일 것" | 가장 약함 → 반드시 검증 필요 |

출처: [Deductive/Inductive/Abductive (Butte College)](https://www.butte.edu/departments/cas/tipsheets/thinking/reasoning.html)

> 실무 흐름: **가추**로 가설 세우고 → **연역**으로 "그게 맞다면 이런 결과여야"를 도출 →
> **측정/귀납**으로 확인. (lab-benchmarks가 바로 이 검증 단계)

### First-Principles (밑바닥부터)

남의 결론·유추를 빌리지 말고 **부정할 수 없는 기본 사실까지 쪼갠 뒤** 다시 쌓는다.
- "다들 Redis 쓰니까" (유추) ❌ → "동시성=정합성 문제고, 우리 앱은 단일 DB다 →
  DB 락이면 충분" (기본 사실에서 재구성) ✅
- 카파시의 "직접 구현해 이해" 와 같은 정신. ([karpathy-approach](../appendix/c2-curriculum-and-nn-types.md))

### 연습법 — LLM과 함께 쓰되 사고를 지키기

1. **가설 먼저, 답은 나중**: LLM에 묻기 전에 **내 답·이유를 한 줄 적는다.** 그다음 비교.
2. **검증을 의무화**: LLM 답을 받으면 "반례는? 근거의 근거는? 직접 재현되나?" (이 세션 내내 한 것)
3. **Feynman 기법**: 배운 걸 **남에게 가르치듯** 내 말로 써본다 (이 레포 자체가 그 도구).
4. **Steelman**: 반대 입장을 **가장 강하게** 만들어보고 그래도 내 결론이 서는지 본다.
5. **판단을 위탁하지 않기**: 근거 수집은 LLM, **"그래서 어떻게 할지" 결정은 내가.**

### 우리 레포에 어떻게 쓰이나

- 트레이드오프 판단 = 가추(가설) + 연역(원칙 적용) + 귀납·측정(검증).
- 단순함 원칙([simplicity-principles](../part3/ch10-design-starting-point.md))의 "지금 필요한가?"
  판단이 곧 추론. 원칙은 도구, **고르는 건 추론.**
