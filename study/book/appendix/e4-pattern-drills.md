| 지문 신호 | 판단 |

| "최대/최소 가치" + **선택이 자원(용량·기회)을 소모** | DP ⭕ — [그리디 드릴](e4-pattern-drills.md)의 실패 신호가 곧 DP 신호 |

### 1단계. 🤔 생각 — 도입: 계단 오르기로 틀 잡기

*(한 번에 1칸 또는 2칸. n칸 오르는 방법 수. dp[i]를 한 문장으로 정의해 보라.)*

<details><summary>📖 추론 열기</summary>

**정의**: `dp[i] = "i번째 칸에 도달하는 방법의 수"`. 마지막 걸음은 1칸이었거나 2칸이었거나 둘뿐이고 겹치지 않으므로 —

```
dp[i] = dp[i-1] + dp[i-2]      (마지막 걸음으로 분류 — 빠짐없이, 겹침없이)
```

> **"마지막 행동으로 분류"**가 점화식 유도의 만능 손잡이다. [카운팅 DP 기출](e3-past-problems.md)도 "마지막 글자로 분류"였다 — 같은 손, 다른 문제.

</details>

**✅ 확인**: dp[1]=1, dp[2]=2, dp[3]=3, dp[4]=5 — 피보나치. n=3을 직접 나열(1+1+1, 1+2, 2+1)해서 3 확인.

### 2단계. 🤔 생각 — 본체: 0/1 배낭. 상태에 왜 차원이 하나 더 붙나?

*(무게 w[i]·가치 v[i]인 물건들, 용량 C 배낭, 가치 최대화. dp[i]만으로 안 되는 이유는?)*

<details><summary>📖 추론 열기</summary>

"i번째까지의 최대 가치"만 알면 **남은 용량을 모르기 때문에** 다음 물건을 넣을 수 있는지 판단 불가. 미래 판단에 필요한 정보가 상태에 다 들어가야 한다:

**정의**: `dp[i][c] = "앞의 i개 물건만 고려하고, 용량 c를 쓸 수 있을 때의 최대 가치"`

마지막 행동(i번째 물건)으로 분류하면 — 안 넣는다 / 넣는다:

```
dp[i][c] = max( dp[i-1][c],                    // i번째를 안 넣음
                dp[i-1][c - w[i]] + v[i] )     // 넣음 (c >= w[i]일 때만)
```

> **상태 설계 원칙**: "이 시점 이후의 결정에 영향을 주는 과거 정보"가 전부 상태에 들어가야 한다 — 격자 탐색에서 (위치+열쇠)로 방문 차원을 늘리던 것과 같은 원리다.

</details>

**✅ 확인**: 점화식의 두 갈래가 "빠짐없이·겹침없이"인지 — i번째 물건의 운명은 넣거나 안 넣거나 둘뿐 ✓

---

### 3단계. 결론 — 코드: 1차원 압축 + **역순의 이유** (Java)

`dp[i][*]`는 `dp[i-1][*]`만 참조하므로 1차원으로 압축되는데, **순회 방향이 정답의 갈림길**이다:

```java
static int knapsack(int C, int[] w, int[] v) {
    int[] dp = new int[C + 1];                    // dp[c] = 용량 c의 최대 가치
    for (int i = 0; i < w.length; i++)
        for (int c = C; c >= w[i]; c--)           // ★ 역순! 이유는 아래
            dp[c] = Math.max(dp[c], dp[c - w[i]] + v[i]);
    return dp[C];
}
```

**왜 역순인가**: `dp[c - w[i]]`는 **이전 물건까지의 값(i-1 행)**이어야 한다. 정순으로 돌면 방금 이번 물건으로 갱신한 값을 다시 읽어 — **같은 물건을 여러 번 넣는 셈**이 된다. (뒤집어 말하면: **물건을 무한정 넣을 수 있는 "완전 배낭"은 일부러 정순으로 돈다** — 방향 하나가 문제 종류를 가른다.)

---

### 4단계. ✅ 전체 확인 — C=5, 물건 (w,v) = (2,3), (3,4), (4,5)

| 처리 후 | dp[0..5] |
|---|---|
| 초기 | 0 0 0 0 0 0 |
| (2,3) | 0 0 3 3 3 3 |
| (3,4) | 0 0 3 4 4 **7** |
| (4,5) | 0 0 3 4 5 7 |

**답: dp[5] = 7** ((2,3)+(3,4) = 무게 5, 가치 7 ✓ — (4,5) 단독 5보다 큼)

---

### 5단계. 함정 체크리스트

- [ ] **0/1 배낭 = 역순, 완전 배낭 = 정순** — 방향 실수가 곧 다른 문제의 답
- [ ] 상태 정의 문장을 주석으로 코드 위에 먼저 쓰기 — 디버깅의 기준점
- [ ] dp 배열 크기 `C+1` (용량 0 포함), 초기값이 0인 게 맞는 문제인지 (불가능 상태를 −∞로 둬야 하는 변형)
- [ ] 가치 합이 int를 넘는 입력 규모면 long
- [ ] "방법의 수"를 물으면 max 대신 **덧셈** — 최적화 DP와 카운팅 DP의 갈림 ([기출](e3-past-problems.md))

### 3단 요약 (암기)

- **① 결론 · WHAT** — 테이블 DP는 ① 상태를 한국어 한 문장으로 정의 ② **마지막 행동으로 분류**해 점화식 ③ 참조 방향에 맞는 순회 — 의 3단계다. 배낭은 `dp[c] = max(안 넣음, dp[c−w]+v)`에 **역순 순회**.
- **② 원리 · HOW** — 상태에는 "미래 결정에 필요한 과거 정보 전부"가 들어가야 한다(그래서 배낭엔 용량 차원 추가). 역순의 이유는 1차원 압축에서 `dp[c−w]`가 이전 행 값으로 남아 있어야 하기 때문 — 정순은 같은 물건 중복 사용(=완전 배낭)이 된다.
- **③ 확장 · TRADE-OFF** — 그리디 실패 신호(선택이 자원 소모)가 곧 DP 신호다. 같은 틀에서 LIS(상태=끝 원소), 편집 거리(2차원 문자열)로 확장되고, 상태 공간이 너무 크면(10⁹ 용량) DP가 아니라 [파라메트릭 이분탐색](e4-pattern-drills.md)이나 그리디 재검토 신호다 — 상태 크기 견적이 판별의 마지막 관문.

## 유형 훈련 — 그리디: "왜 이 정렬이 최적인가"를 한 줄로

> 백로그 4번 — [로드맵 D10](e2-coding-test-2week.md)의 실전판. 실습 문제: 회의실 배정 (프로그래머스/백준 1931 동형).
> **난이도**: 프로그래머스 **Lv2** · 기업 2번(중) — 코드는 5줄인데 **증명을 못 하면 틀린 정렬 기준을 골라 전멸**하는 유형.
> 진행: **🤔 생각 → 📖 읽기 → ✅ 확인** 순서.

---

### 0단계. 판별 — 지문 신호

| 지문 신호 | 판단 |
|---|---|
| "최대 **개수**를 선택하라" (겹치지 않게) | 그리디 후보 ⭕ |
| 정렬하고 앞에서부터 취하면 될 것 같은 직감 | 후보 ⭕ — 단 **증명 전엔 확정 금지** |
| 지금의 선택이 **미래의 용량/기회를 소모**한다 (배낭처럼) | ❌ 그리디 실패 신호 → DP로 |
| 부분 문제의 답을 **되돌릴 일이 없다** | 그리디 성립 방향 |

> 판별 한 줄: **"욕심내도 나중에 후회가 없음"을 증명할 수 있을 때만 그리디다.** 증명 도구가 이 드릴의 본체인 교환 논증(exchange argument).

---

### 1단계. 🤔 생각 — 회의실 배정, 무엇으로 정렬하나?

*(회의 [시작,끝] n개, 겹치지 않게 최대 개수. 후보: ① 시작 빠른 순 ② 짧은 순 ③ 끝나는 순. 각각 반례를 만들어 보라.)*

<details><summary>📖 추론 열기</summary>

**① 시작 순 반례**: `[1,100], [2,3], [4,5]` — 시작 빠른 [1,100]을 잡으면 1개, 답은 2개.
**② 짧은 순 반례**: `[1,10], [9,12], [11,20]` — 가장 짧은 [9,12]를 잡으면 1개, 답은 2개 ([1,10]+[11,20]).
**③ 끝나는 순** — 반례가 안 만들어진다. 왜인지가 핵심:

> **교환 논증**: 어떤 최적해가 있다고 하자. 그 최적해의 첫 회의를 "가장 일찍 끝나는 회의"로 **바꿔치기**해도 — 더 일찍 끝나니 뒤의 모든 회의는 그대로 유효하다. 즉 **손해가 없다.** 같은 논리를 두 번째, 세 번째에 반복하면: "끝나는 순 그리디 해"는 어떤 최적해와도 개수가 같다. ∎

이게 그리디 증명의 표준 틀이다: **"최적해를 내 선택으로 한 조각씩 교환해도 나빠지지 않음"**을 보인다. 시험장에선 엄밀 증명 대신 이 한 문장 — *"가장 일찍 끝나는 걸 잡는 게 미래의 선택지를 최대로 남긴다"* — 을 말할 수 있으면 된다.

</details>

**✅ 확인**: ①②의 반례를 내 손으로 재현 — **틀린 기준이 왜 틀리는지**를 아는 게 맞는 기준을 외우는 것보다 오래 간다.

---

### 2단계. 결론 — 코드 (Java)

```java
static int maxMeetings(int[][] m) {
    Arrays.sort(m, (a, b) -> a[1] != b[1] ? a[1] - b[1] : a[0] - b[0]);  // 끝나는 시간 순
    int count = 0, lastEnd = Integer.MIN_VALUE;
    for (int[] x : m)
        if (x[0] >= lastEnd) {        // 이전 회의가 끝난 뒤 시작하면
            count++;
            lastEnd = x[1];           // 채택하고 기준 갱신
        }
    return count;
}
```

정렬 O(n log n) + 한 번 순회 — 그리디의 전형적 모양: **정렬이 알고리즘의 전부이고, 루프는 확인일 뿐.**

---

### 3단계. ✅ 전체 확인 — 손 추적

회의 `[1,4] [3,5] [0,6] [5,7] [8,9] [5,9]` → 끝 시간 정렬: `[1,4] [3,5] [0,6] [5,7] [5,9] [8,9]`

| 회의 | 시작 ≥ lastEnd? | 채택 | lastEnd |
|---|---|---|---|
| [1,4] | ✓ | 1 | 4 |
| [3,5] | `3 < 4` ✗ | — | 4 |
| [0,6] | ✗ | — | 4 |
| [5,7] | 5 ≥ 4 ✓ | 2 | 7 |
| [5,9] | ✗ | — | 7 |
| [8,9] | 8 ≥ 7 ✓ | **3** | 9 |

**답: 3**

---

### 4단계. 함정 체크리스트

- [ ] **"끝나는 시간이 같으면 시작 순" 2차 정렬** — `[2,2]`처럼 시작=끝인 회의가 섞이면 순서에 따라 답이 달라질 수 있음
- [ ] 경계: "끝나는 순간 시작" 허용 여부 (`>=` vs `>`) — 지문 확인
- [ ] **그리디 실패 신호를 놓치지 않았나** — 선택이 무게/용량을 소모하면(0/1 배낭) 그리디 반례 존재 → [DP 테이블 드릴](e4-pattern-drills.md)
- [ ] 최소 회의실 **개수**를 묻는 변형은 다른 문제 (시작·끝 이벤트 스위프 or 힙 — [힙 드릴](e4-pattern-drills.md))

---

### 3단 요약 (암기)

- **① 결론 · WHAT** — 그리디는 "정렬 기준 선택 + 그 기준이 최적인 이유 한 줄"이 전부다. 회의실 배정은 **끝나는 시간 순** — "가장 일찍 끝나는 걸 잡아야 미래 선택지가 최대"이기 때문.
- **② 원리 · HOW** — 증명 틀은 **교환 논증**: 임의의 최적해에서 첫 선택을 내 그리디 선택으로 바꿔도 손해가 없음을 보이고 귀납 반복. 시험장 버전은 "바꿔치기해도 안 나빠진다" 한 문장.
- **③ 확장 · TRADE-OFF** — 그리디의 위험은 **그럴듯한데 틀린 기준**이다(시작 순·짧은 순 반례). 판별법: 반례를 30초 못 만들겠으면 교환 논증을 시도하고, 선택이 미래 자원을 소모하는 구조(배낭)면 미련 없이 DP로 — 그리디와 DP의 경계 감각 자체가 이 유형의 득점 포인트다.

## 유형 훈련 — 격자 BFS/DFS (섬 개수 · 최단 거리)

> 백로그 1번 — **기업 2번 문제 최다 빈출인데 드릴이 없던 유형**.
> **난이도**: 프로그래머스 **Lv2** · HackerRank Medium · 기업 2번(중) — 미로·지도·전염 확산·게임 맵이 전부 이 유형의 옷만 바꾼 것.
> 진행: **🤔 생각 → 📖 읽기 → ✅ 확인** 순서.

---

### 0단계. 판별 — 지문 신호

격자(2차원 배열) + 아래 문구가 보이면 이 유형이다:

| 지문 신호 | 알고리즘 | 이유 |
|---|---|---|
| "**몇 개의 덩어리/구역/섬**인가" | DFS 또는 BFS (아무거나) | 연결된 것 전부 방문 표시만 하면 됨 (flood fill) |
| "**최단 거리 / 최소 이동 횟수**" | **BFS 고정** | 아래 1단계 — DFS로 하면 틀린다 |
| "칸마다 이동 **비용이 다르다**" | 다익스트라 (3번 급) | BFS는 비용 균일일 때만 최단 — 여기선 신호만 알면 됨 |
| "모든 경로/경우의 수를 세라" | DFS+백트래킹 | 탐색이 아니라 열거 문제 |

> 판별 핵심 한 줄: **세는 문제는 아무거나, 최단은 BFS, 비용 다르면 여기가 아니다.**

---

### 1단계. 🤔 생각 — "최단"이면 왜 DFS가 안 되나?

*(DFS도 결국 도착점에 도달하는데, 왜 최단 거리는 못 구하나?)*

<details><summary>📖 추론 열기</summary>

DFS는 **한 방향으로 끝까지** 파고든다 — 처음 도착한 경로는 "아무 경로"지 최단이 아니다. 모든 경로를 다 뒤져 최솟값을 갱신하면 되긴 하지만 지수 시간이다.

BFS는 **거리 순서대로** 퍼진다: 시작점에서 거리 1인 칸을 전부 → 거리 2를 전부 → … 그러므로 —

> **BFS에서 어떤 칸에 처음 도달한 순간, 그 거리가 곧 최단 거리다.** 증명이 큐의 성질에서 공짜로 나온다: 큐에는 항상 "거리 d와 d+1인 칸들만" 순서대로 들어 있다.

이게 "최단 = BFS 고정"의 이유이고, 가중치가 붙는 순간 이 증명이 깨지므로(가까운 칸이 더 비쌀 수 있음) 다익스트라로 넘어가는 것이다.

</details>

**✅ 확인**: "BFS는 왜 처음 도달 = 최단인가?"를 큐 그림 없이 한 문장으로 말해보기 — "거리 순서대로 방문하니까"가 나오면 통과.

### 2단계. 🤔 생각 — 방문 체크는 큐에서 꺼낼 때? 넣을 때?

*(visited 표시 위치가 두 군데 가능하다. 어느 쪽이어야 하고, 틀리면 무슨 일이 나나?)*

<details><summary>📖 추론 열기</summary>

**넣을 때(offer 직전) 표시해야 한다.** 꺼낼 때 표시하면 — 같은 칸이 방문 표시되기 전에 **여러 이웃이 그 칸을 중복으로 큐에 넣는다.** 답은 맞지만 큐가 수십 배로 부풀어 **시간 초과의 단골 원인**이 된다 (격자가 크면 치명적).

> 불변식으로 기억: **"큐 안에 같은 칸은 절대 두 번 없다"** — 이 불변식은 넣을 때 표시해야만 유지된다. ([슬라이딩 윈도우 드릴](e3-past-problems.md)의 "창 안엔 중복 없음"과 같은 사고 — 자료구조의 불변식을 정하고 매 턴 복구한다.)

</details>

**✅ 확인**: 3×3 전부 빈 격자에서 중앙 시작 BFS를 손으로 — 꺼낼 때 표시 방식이면 모서리 칸이 큐에 2번 들어가는 걸 직접 목격할 것.

### 3단계. 결론 — 템플릿 2벌 (Java)

#### ① 섬 개수 (flood fill — DFS판)

```java
static int[][] g; static boolean[][] vis; static int n, m;
static final int[] dr = {-1, 1, 0, 0}, dc = {0, 0, -1, 1};   // 상하좌우 (대각선이면 8방향)

static int countIslands() {
    int count = 0;
    for (int r = 0; r < n; r++)
        for (int c = 0; c < m; c++)
            if (g[r][c] == 1 && !vis[r][c]) { dfs(r, c); count++; }  // 새 덩어리 발견
    return count;
}
static void dfs(int r, int c) {
    vis[r][c] = true;
    for (int d = 0; d < 4; d++) {
        int nr = r + dr[d], nc = c + dc[d];
        if (nr >= 0 && nr < n && nc >= 0 && nc < m && g[nr][nc] == 1 && !vis[nr][nc])
            dfs(nr, nc);
    }
}
```

#### ② 최단 거리 (BFS판 — dist 배열이 visited 겸용)

```java
static int bfs(int sr, int sc, int tr, int tc) {
    int[][] dist = new int[n][m];
    for (int[] row : dist) Arrays.fill(row, -1);      // -1 = 미방문
    ArrayDeque<int[]> q = new ArrayDeque<>();
    dist[sr][sc] = 0; q.offer(new int[]{sr, sc});     // ★ 넣을 때 표시 (2단계)
    while (!q.isEmpty()) {
        int[] cur = q.poll();
        for (int d = 0; d < 4; d++) {
            int nr = cur[0] + dr[d], nc = cur[1] + dc[d];
            if (nr >= 0 && nr < n && nc >= 0 && nc < m
                    && g[nr][nc] != WALL && dist[nr][nc] == -1) {
                dist[nr][nc] = dist[cur[0]][cur[1]] + 1;
                q.offer(new int[]{nr, nc});
            }
        }
    }
    return dist[tr][tc];                              // -1이면 도달 불가
}
```

`dr/dc` 방향 배열이 이 유형 전체의 관용구다 — if문 4개 복붙 대신 루프 하나.

격자 `(1=땅, 0=바다)`:

```
1 1 0        섬 개수: (0,0)에서 DFS → (0,1)까지 방문 = 덩어리 1
0 0 1        (1,2)에서 DFS → (2,2)까지 방문 = 덩어리 2
0 1 1        답: 2
```

최단 거리(전부 이동 가능, (0,0)→(2,2)): BFS 레벨 확산 `0→1→2→3→4` — 거리 4 (맨해튼 거리와 일치하는지로 검산).

### 5단계. 함정 체크리스트

- [ ] **방문 표시는 큐에 넣을 때** (꺼낼 때 표시 = 시간 초과 1순위 원인)

- [ ] (row, col) 순서 — 입력이 (x,y)로 주어져도 내부에선 `g[행][열]`로 통일하고 변환 지점을 한 곳으로
- [ ] **대각선 포함 여부** 지문 확인 — 방향 배열만 8개로 교체
- [ ] 시작점이 여러 개인 변형(전염 확산·불) — 전부 큐에 넣고 시작하는 **멀티소스 BFS** (같은 템플릿)

- **① 결론 · WHAT** — 격자 문제는 두 질문으로 갈린다: **덩어리 세기 = flood fill(DFS/BFS 아무거나), 최단 거리 = BFS 고정.** 방향 배열 `dr/dc` + "넣을 때 방문 표시"가 템플릿의 전부다.
- **② 원리 · HOW** — BFS는 큐 성질상 **거리 순서대로** 방문하므로 첫 도달이 곧 최단이다(가중치 균일일 때만 — 깨지면 다익스트라). 방문 표시를 넣을 때 하는 이유는 "큐 안에 같은 칸 없음" 불변식 — 어기면 답은 맞아도 큐 폭발로 시간 초과.
- **③ 확장 · TRADE-OFF** — DFS 재귀는 짧지만 큰 격자에서 스택오버플로 위험(명시적 스택/BFS로 회피), BFS는 큐 메모리를 먹는다. 변형 감각: 시작점 여러 개면 멀티소스 BFS, 상태가 (위치+열쇠소지) 같은 복합이면 방문 배열 차원을 늘린다 — 템플릿은 같고 **"상태가 무엇인가"만 다시 정의**하면 된다.

### 1단계. 🤔 생각 — 왜 "직접 계산"이 막히고, 뒤집으면 뚫리나?

*(위 기계 문제에서 최소 일수를 바로 구하는 식을 세워 보라. 잘 안 될 것이다. 그런데 "d일이면 목표를 채우나?"는?)*

<details><summary>📖 추론 열기</summary>

정방향("최소 일수 = ?")은 기계마다 주기가 달라 닫힌 식이 없다. 그런데 역방향은 허무할 만큼 쉽다:

```
d일 동안의 총 생산량 = Σ (d / a[i])     ← O(n) 한 줄
가능(d) = (총 생산량 >= goal)
```

그리고 이 판정은 **단조**다 — d일에 가능하면 d+1일엔 당연히 가능. 즉 수직선이 이렇게 생겼다:

```
d:        1  2  3  4  5  6  7  8 ...
가능?     ✗  ✗  ✗  ✓  ✓  ✓  ✓  ✓
                   ↑ 이 경계가 답 — "정렬된 것"은 배열이 아니라 이 ✗✗✗✓✓✓ 구조다
```

✗✗✗✓✓✓에서 경계 찾기 = 이분탐색. **어려운 최적화 문제가 "쉬운 판정 문제 × log번"으로 분해**된 것이다.

> [이진 조합 드릴](e3-past-problems.md)의 "만들지 말고 세라", [REST API 드릴](e3-past-problems.md)의 "모으고 나서 판단하라"에 이어 — 이 유형의 전환은 **"계산하지 말고 검증하라"**다. 세 드릴이 같은 메타 패턴: 정면돌파가 막히면 문제를 뒤집는다.

</details>

**✅ 확인**: 기계 a=[2,3], goal=5로 가능(d)를 손 계산 — d=6: 6/2+6/3 = 3+2 = 5 ✓ / d=5: 2+1=3 ✗. 경계는 6.

### 2단계. 🤔 생각 — lo/hi 갱신에서 왜 `hi = mid`고 `lo = mid + 1`인가?

*(가능하면 hi=mid, 불가능하면 lo=mid+1. mid-1이나 mid로 안 하는 이유는?)*

<details><summary>📖 추론 열기</summary>

**불변식으로 설계**하면 헷갈리지 않는다: "**답은 항상 [lo, hi] 안에 있다**"를 매 턴 유지한다.

- `가능(mid)` → mid가 답일 **수도** 있다 → 버리면 안 됨 → `hi = mid` (mid 포함 유지)
- `불가능(mid)` → mid는 절대 답이 아님 → `lo = mid + 1` (mid 제외)
- 종료: `lo == hi` — 구간이 한 점으로 줄면 그게 답

```java
long lo = 1, hi = MAX;                    // 답이 반드시 존재하는 범위로 초기화
while (lo < hi) {
    long mid = lo + (hi - lo) / 2;        // (lo+hi)/2는 오버플로 위험
    if (possible(mid)) hi = mid;          // 답 후보 — 포함한 채 좁힘
    else lo = mid + 1;                    // 답 아님 — 확실히 버림
}
return lo;                                // lo == hi == 최솟값
```

"최댓값을 구하라"(반대 방향 ✓✓✓✗✗✗)면 대칭으로 `lo = mid`(가능 시) / `hi = mid - 1`, 이때 `mid = lo + (hi - lo + 1) / 2`로 올림해야 무한 루프가 안 난다.

</details>

**✅ 확인**: 무한 루프 검산 — lo=4, hi=5일 때 mid=4: 가능이면 hi=4(수렴), 불가능이면 lo=5(수렴). 어느 쪽도 구간이 줄었는지 확인.

### 3단계. 결론 — 전체 코드 (Java)

```java
static long minDays(int[] a, long goal) {
    long lo = 1, hi = (long) goal * min(a);          // 상한: 가장 빠른 기계 혼자 다 만드는 시간
    while (lo < hi) {
        long mid = lo + (hi - lo) / 2;
        if (produced(a, mid) >= goal) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}
static long produced(int[] a, long d) {              // 판정 함수 — 이 문제의 진짜 본체
    long sum = 0;
    for (int x : a) {
        sum += d / x;
        if (sum >= Integer.MAX_VALUE) return sum;    // 조기 종료 겸 오버플로 방어
    }
    return sum;
}
```

구조가 항상 같다: **껍데기(이분탐색 7줄)는 복붙, 문제마다 새로 쓰는 건 `possible()` 하나.**

### 5단계. 함정 체크리스트

- [ ] **단조성 확인 없이 적용하지 않았나** — 가능/불가능이 ✗✓✗처럼 오락가락하면 이분탐색 자체가 무효 (이게 성립 조건이다)
- [ ] `mid = lo + (hi - lo) / 2` — `(lo+hi)/2`는 **오버플로**
- [ ] 판정 함수 내부 합계는 **long** (d가 10⁹이면 d/x 합이 int를 순식간에 넘음)
- [ ] 상한(hi) 초기값이 **답을 반드시 포함**하는가 — 애매하면 넉넉히 (log라 비용 미미)
- [ ] 최댓값 버전에서 `mid` **올림** 안 하면 무한 루프
- [ ] 답이 존재하지 않을 수 있는 문제인가 — 종료 후 `possible(lo)` 한 번 더 검증

### 3단 요약 (암기)

- **① 결론 · WHAT** — "~한 최솟값/최댓값"인데 직접 계산식이 없으면 **"답이 x일 때 가능한가?"로 뒤집어라.** 판정이 O(n)·단조면 이분탐색으로 O(n log MAX) — 껍데기는 복붙이고 문제의 본체는 `possible()` 하나다.
- **② 원리 · HOW** — 정렬된 것은 배열이 아니라 **가능/불가능의 ✗✗✗✓✓✓ 경계 구조**다. 루프는 "답은 [lo, hi] 안"이라는 불변식 유지로 설계한다: 가능이면 후보 포함(`hi=mid`), 불가능이면 확실 제외(`lo=mid+1`), 한 점 수렴이 답.
- **③ 확장 · TRADE-OFF** — 성립 조건은 **단조성** — 깨지면 무효라 판별 단계에서 반드시 확인한다. 같은 전환으로 "가장 가까운 정거장 최대 거리", "예산 상한" 류가 전부 풀리며, 판정 함수가 O(n log n)이어도 총합은 여전히 싸다. [격자 BFS](e4-pattern-drills.md)·[윈도우](e3-past-problems.md)와 함께 "**불변식으로 루프를 설계한다**"는 공통 근육을 훈련하는 유형이다.

| 구간 **질의가 여러 번** (l, r 합) | 누적합 배열만 (해시 불필요) — [D8](e2-coding-test-2week.md) |

### 1단계. 🤔 생각 — 음수가 섞이면 윈도우는 왜 죽나?

*(윈도우가 성립하려면 "창을 늘리면 합이 커지고, 줄이면 작아진다"가 필요하다. 음수가 있으면?)*

<details><summary>📖 추론 열기</summary>

윈도우의 엔진은 **단조성**이다: 합이 크면 왼쪽을 당기고, 작으면 오른쪽을 늘린다 — 이 판단은 "늘리면 커진다"가 보장될 때만 유효하다. 음수가 섞이면 **창을 늘렸는데 합이 줄어들 수 있어** 어느 쪽으로 움직일지 판단 근거가 사라진다.

> [파라메트릭 이분탐색](e4-pattern-drills.md)의 성립 조건이 판정의 단조성이었듯, **윈도우의 성립 조건은 창-합의 단조성**이다. 도구마다 "성립 조건"이 있고, 판별이란 그 조건을 검사하는 일이다.

</details>

**✅ 확인**: `[1, -1, 1]`에서 합 1인 창을 윈도우로 쫓아가 보라 — 창을 어떻게 움직여도 [1], [1,-1,1], [1]（뒤） 세 개를 일관된 규칙으로 못 잡는다.

---

### 2단계. 🤔 생각 — 그럼 무엇으로 바꾸나?

*(구간 합 = 누적합의 차: sum(i..j) = pre[j] - pre[i-1]. "합이 K인 구간의 개수"를 이 식으로 다시 써 보라.)*

<details><summary>📖 추론 열기</summary>

`pre[j] - pre[i] = K`  ⇔  `pre[i] = pre[j] - K`. 그러므로 j를 왼쪽부터 훑으며 —

> **"지금 누적합 − K 값을, 과거에 몇 번 봤는가?"** — 그 횟수가 j에서 끝나는 정답 구간의 개수다. 과거 누적합의 등장 횟수를 HashMap에 쌓으면 O(n).

이는 two-sum의 일반화이자, [Sherlock 드릴](e3-past-problems.md)의 "쌍을 직접 세지 말고 그룹으로" 사고와 동일하다 — **쌍 (i,j)를 열거하지 않고, j 시점에 '짝이 될 수 있는 i의 개수'를 조회**한다.

</details>

**✅ 확인**: 왜 map에 `{0: 1}`을 미리 넣어야 하나? — `pre[j] = K`인 순간(배열 처음부터 j까지가 정답 구간)에 `pre[j]-K = 0`을 찾게 되는데, "아무것도 안 더한 상태"도 한 번 등장한 누적합이기 때문. 이 초기값 누락이 이 유형 오답 1위다.

---

### 3단계. 결론 — 코드 (Java)

```java
static long countSubarrays(int[] a, long k) {
    Map<Long, Integer> seen = new HashMap<>();
    seen.put(0L, 1);                          // ★ 빈 접두사 — 처음부터 시작하는 구간용
    long pre = 0, count = 0;
    for (int x : a) {
        pre += x;
        count += seen.getOrDefault(pre - k, 0);   // 짝이 되는 과거 누적합 조회
        seen.merge(pre, 1, Integer::sum);         // 지금 누적합을 과거 목록에 등록
    }
    return count;
}
```

조회가 등록보다 **먼저**다 — 순서를 바꾸면 K=0일 때 자기 자신과 짝지어 오답.

---

### 4단계. ✅ 전체 확인 — a=[1,2,3], K=3 손 추적

| x | pre | pre−K 조회 | count | map 등록 후 |
|---|---|---|---|---|
| — | 0 | — | 0 | {0:1} |
| 1 | 1 | −2 → 0회 | 0 | {0:1, 1:1} |
| 2 | 3 | 0 → **1회** | 1 | {0:1, 1:1, 3:1} |
| 3 | 6 | 3 → **1회** | **2** | {…, 6:1} |

**답: 2** — 구간 [1,2]와 [3] ✓

---

### 5단계. 함정 체크리스트

- [ ] **`seen.put(0L, 1)` 초기값** — 누락하면 "처음부터 시작하는 구간"이 전부 빠짐 (오답 1위)
- [ ] **조회 → 등록 순서** — 바꾸면 K=0에서 자기 매칭
- [ ] 누적합·개수는 **long** (10⁵개 × 10⁹ 값)
- [ ] "개수"가 아니라 "**최장 길이**"를 묻는 변형 → map에 개수 대신 **최초 등장 인덱스** 저장
- [ ] 전부 양수라고 명시돼 있으면 윈도우도 정답 — 더 익숙한 쪽으로 (판별표 참조)

---

### 3단 요약 (암기)

- **① 결론 · WHAT** — 음수 섞인 "합이 K인 연속 구간"은 윈도우가 아니라 **누적합+해시**: `pre−K`를 과거에 본 횟수를 세면 O(n).
- **② 원리 · HOW** — 윈도우의 성립 조건(창-합 단조성)이 음수에서 깨지므로, 구간 합을 **누적합의 차**로 바꿔 "쌍 열거"를 "과거 조회"로 치환한다. `{0:1}` 초기값은 빈 접두사의 등장을 의미한다.
- **③ 확장 · TRADE-OFF** — 같은 틀로 "합이 K의 배수인 구간"(누적합을 mod로 저장), "0과 1 개수가 같은 구간"(0을 −1로 치환) 등이 전부 풀린다. 대가는 HashMap 메모리 O(n) — 그리고 이 유형의 진짜 시험은 코드가 아니라 **윈도우/누적합 판별을 30초 안에 끝내는 것**이다.

### 0단계. 판별 — 지문 신호

| 지문 신호 | 판단 |
|---|---|
| "**가장 작은/큰 것을 꺼내 → 가공 → 다시 넣기**를 반복" | 힙 확정 (이 드릴의 본체) |

### 1단계. 🤔 생각 — 매번 정렬하면 왜 안 되나?

*(원소를 꺼내고 새 원소를 넣을 때마다 `Collections.sort()`를 다시 부르면? 복잡도를 계산해 보라.)*

<details><summary>📖 추론 열기</summary>

n개 원소에 n번의 갱신이 일어나면 매번 정렬은 **O(n × n log n)** — 10⁵개면 시간 초과 확정. 낭비의 정체는:

> 정렬은 **전체 순서**를 만드는데, 우리가 쓰는 건 매번 **맨 앞 하나**뿐이다. 필요한 것보다 훨씬 강한 것을 계산하고 있다.

힙은 "최솟값이 루트에 있다"는 **느슨한 순서만** 유지한다 — 그래서 꺼내기·넣기가 O(log n), 전체 O(n log n). ([이진 조합](e3-past-problems.md)의 "필요한 것만 계산하라"와 같은 절약 원리다.)

</details>

**✅ 확인**: Java에서 `PriorityQueue`의 `peek()`은 O(1), `poll()`/`offer()`는 O(log n) — 그리고 **최대힙은 생성자에 `Comparator.reverseOrder()`** (기본이 최소힙이라는 것, 시험장 1분 함정).

### 2단계. 결론 — Jesse and Cookies (Java)

> 문제: 과자들의 단맛 배열. **가장 안 단 과자 둘을 꺼내** `새 과자 = 1번째 + 2×2번째`로 합치는 연산을, 모든 과자가 K 이상이 될 때까지 반복. 최소 연산 횟수는? (불가능하면 -1)

```java
static int cookies(int k, int[] a) {
    PriorityQueue<Long> pq = new PriorityQueue<>();          // 기본 = 최소힙
    for (int x : a) pq.offer((long) x);
    int ops = 0;
    while (pq.peek() < k) {                                  // 아직 목표 미달
        if (pq.size() < 2) return -1;                        // ★ 합칠 게 없음 = 불가능
        long first = pq.poll(), second = pq.poll();
        pq.offer(first + 2 * second);
        ops++;
    }
    return ops;
}
```

---

### 3단계. ✅ 전체 확인 — a=[1,2,3,9,10,12], K=7 손 추적

| 연산 | 꺼낸 둘 | 새 과자 | 힙 상태 | 최솟값 ≥ 7? |
|---|---|---|---|---|
| 1 | 1, 2 | 1+2×2=**5** | [3,5,9,10,12] | 3 ✗ |
| 2 | 3, 5 | 3+2×5=**13** | [9,10,12,13] | 9 ✓ |

**답: 2** (HackerRank 공식 예제와 일치)

---

### 4단계. 함정 체크리스트

- [ ] **원소 1개 남았는데 목표 미달** → `size() < 2` 검사 없이 poll 두 번 하면 NPE. -1 반환 조건
- [ ] 합성값은 **long** — 단맛이 커지면 int 초과
- [ ] 최대힙 필요할 때 `new PriorityQueue<>(Comparator.reverseOrder())` — 기본은 최소힙
- [ ] `peek()`으로 검사, `poll()`로 제거 — peek 자리에 poll 쓰면 원소가 증발
- [ ] "K번째" 변형: **크기 K를 유지하는 반대 방향 힙** (K번째로 큰 값 = 크기 K 최소힙의 루트)

---

### 3단 요약 (암기)

- **① 결론 · WHAT** — "매번 최솟값(최댓값)을 꺼내 가공 후 재삽입"이 반복되면 힙. 반복문 안에서 sort를 또 부르고 싶은 충동이 곧 판별 신호다.
- **② 원리 · HOW** — 정렬은 전체 순서(과잉), 힙은 "루트가 최솟값"이라는 느슨한 순서만 유지해 poll/offer O(log n). 필요한 만큼만 계산하는 절약이 O(n²log n)→O(n log n)을 만든다.
- **③ 확장 · TRADE-OFF** — 힙은 **중간 원소 탐색·삭제가 O(n)** — 그게 필요하면 TreeMap. "K번째" 스트림은 크기 K 역방향 힙, 두 힙(최대+최소)을 맞붙이면 중앙값 스트림까지 커버 — 전부 이 템플릿의 변주다.

## 유형 훈련 — 스택 시뮬레이션: "가장 최근 것과 짝짓기"

> 진행: **🤔 생각 → 📖 읽기 → ✅ 확인** 순서.

### 0단계. 판별 — 지문 신호

| 지문 신호 | 판단 |
|---|---|
| "**가장 최근/가장 가까운** 것과 짝·상쇄·제거" | 스택 확정 |

### 1단계. 🤔 생각 — 왜 "지우고 다시 검사"가 스택 한 번으로 끝나나?

<details><summary>📖 추론 열기</summary>

`baab`에서 `aa`를 지우면 `bb`가 새로 붙는다 — 삭제가 **연쇄**를 만든다. 문자열로 구현하면 지울 때마다 처음부터 재검사.

스택으로 보면: 문자를 밀어넣다가 **top과 짝이면 pop**. `aa`가 pop되는 순간 top엔 자동으로 이전 `b`가 드러나 다음 `b`와 만난다 — **연쇄 재검사가 스택 구조 자체에 내장**돼 있다. 각 문자는 최대 1번 push·1번 pop → O(n).

</details>

**✅ 확인**: `baab` 손 추적 — push b, push a, a==top? pop(a), b==top? pop(b) → 빈 스택 = 전부 제거 ✓

---

### 2단계. 결론 — 템플릿 2벌 (Java)

```java
// ① 인접 짝 제거 (같은 문자 만나면 상쇄)
static boolean allRemoved(String s) {
    Deque<Character> st = new ArrayDeque<>();
    for (char c : s.toCharArray()) {
        if (!st.isEmpty() && st.peek() == c) st.pop();   // 짝 — 상쇄
        else st.push(c);
    }
    return st.isEmpty();
}

// ② 괄호 유효성 (여는 건 push, 닫는 건 top과 대조)
static boolean valid(String s) {
    Deque<Character> st = new ArrayDeque<>();
    Map<Character, Character> pair = Map.of(')', '(', ']', '[', '}', '{');
    for (char c : s.toCharArray()) {
        if (!pair.containsKey(c)) st.push(c);
        else if (st.isEmpty() || st.pop() != pair.get(c)) return false;  // ★ 빈 스택 검사 먼저
    }
    return st.isEmpty();                                 // ★ 남으면 미완성 괄호
}
```

### 3단계. 함정 체크리스트

- [ ] **빈 스택에서 pop/peek** — `)`로 시작하는 입력에서 예외. `isEmpty()` 검사가 항상 먼저
- [ ] 루프 끝나고 **스택이 비었는지 최종 확인** — `(((`은 루프에서 안 걸린다
- [ ] `java.util.Stack` 대신 **`ArrayDeque`** (Stack은 동기화 오버헤드 있는 레거시)
- [ ] 문자열 삭제로 구현하지 않았나 — `replace` 반복은 O(n²)

### 3단 요약 (암기)

- **① 결론 · WHAT** — "가장 최근 것과 짝·상쇄"는 스택: push하다 top과 짝이면 pop, O(n). 괄호·인접 제거·수식 계산이 전부 이 틀.
- **② 원리 · HOW** — 상쇄 후 "양옆이 새로 만나는" 연쇄가 스택 top에 자연히 드러나므로 재검사가 공짜다 — 각 원소 push/pop 1회씩이라는 상한이 O(n)의 증명.
- **③ 확장 · TRADE-OFF** — 빈출 확장은 히스토그램 최대 직사각형·오큰수(단조 스택)인데 그건 3번 문제 급 — 2번 대역에선 "빈 스택 검사·최종 잔여 검사" 두 함정만 완벽하면 만점 유형이다.

## 유형 훈련 — 카카오식 문자열 구현: 알고리즘 없는 체력전

### 0단계. 판별 — 지문 신호

| 지문 신호 | 판단 |
|---|---|
| 지문이 **길고** 규칙이 여러 개인데 자료구조 힌트가 없다 | 구현 문제 — 알고리즘 찾느라 시간 쓰지 말 것 |
| "규칙에 따라 변환/시뮬레이션하라" | 구현 확정 |
| 입력 크기가 작다 (n ≤ 1,000) | **복잡도 걱정 불필요 = 정확성 승부**라는 출제자 신호 |

> 판별 한 줄: **지문이 길고 입력이 작으면, 시험 대상은 머리가 아니라 꼼꼼함이다.** 이 순간 전략을 "좋은 알고리즘 찾기"에서 "명세 빠짐없이 옮기기"로 전환한다.

---

### 1단계. 🤔 생각 — 긴 지문을 어떻게 코드로 안전하게 옮기나?

<details><summary>📖 추론 열기</summary>

한 덩어리 main에 다 쓰면 명세 누락을 눈으로 못 찾는다. 전략은 **명세 문장 : 함수 = 1 : 1 분해**:

```
지문의 규칙 ①②③  →  rule1(), rule2(), rule3()  →  각각 예제로 단독 검증  →  조립
```

- 함수 이름을 **지문의 용어 그대로** — "보너스 점수" 규칙이면 `applyBonus()`. 나중에 지문과 코드를 나란히 놓고 대조 가능
- **예제 입출력을 단계별 중간값까지 손으로** 먼저 계산해 두고, 함수 하나 만들 때마다 그 중간값과 대조 — 다 만들고 최종 출력만 비교하면 어느 규칙이 틀렸는지 못 찾는다

> [테스트 전략 노트](../part5/ch17-1-testing-and-standards.md)의 축소판이다 — 단위(규칙별 함수) 검증 후 통합. 시험장에서도 같은 근육.

</details>

**✅ 확인**: 자신의 최근 구현 문제 오답을 복기 — 대부분 "규칙을 잘못 이해"가 아니라 **"규칙 하나를 안 읽음"**이었을 것. 그래서 해법이 알고리즘이 아니라 절차다.

### 2단계. 결론 — 자주 쓰는 파싱 관용구 (Java)

```java
// 숫자·문자 혼합 파싱 (다트게임류): 인덱스 포인터 하나로 훑기
int i = 0;
while (i < s.length()) {
    int start = i;
    while (i < s.length() && Character.isDigit(s.charAt(i))) i++;   // 숫자 구간
    int num = Integer.parseInt(s.substring(start, i));
    char option = s.charAt(i++);                                    // 뒤따르는 기호
    // ... 규칙 적용 ...
}

// 압축류: 길이 k 단위로 자르며 연속 반복 세기
for (int k = 1; k <= s.length() / 2; k++) { /* 단위 k 시도 */ }

// 구분자 파싱: split보다 지문 규칙이 복잡하면 수동 substring이 안전
// (연속 구분자·빈 토큰 처리를 split의 암묵 규칙에 맡기지 말 것)
```

**전역 체크 습관**: 대소문자 구분, 빈 문자열, 경계(마지막 토큰 뒤 구분자 유무), `Integer.parseInt`의 앞자리 0 — 전부 지문에 답이 있다. **모르면 추측 말고 지문을 다시 읽는다.**

### 3단계. 함정 체크리스트

- [ ] 명세 문장마다 **구현했는지 체크 표시**하며 옮겼나 (지문에 연필로 ✓)
- [ ] 예제의 **중간 단계 값**을 손으로 계산해 두고 함수 단위로 대조했나
- [ ] 엣지: 빈 입력·규칙이 한 번도 발동 안 하는 입력·전부 같은 문자
- [ ] `split` 암묵 규칙(끝 빈 토큰 제거 등)에 당하지 않았나 — 복잡하면 수동 파싱
- [ ] 입력이 작다고 확인했나 — 크면 이 유형이 아니라 알고리즘 문제다 (판별 재검토)

### 3단 요약 (암기)

- **① 결론 · WHAT** — 지문 길고 입력 작으면 구현 체력전: 전략을 "알고리즘 찾기"에서 **"명세 문장:함수 = 1:1 옮기기 + 중간값 대조"**로 전환한다.
- **② 원리 · HOW** — 이 유형의 오답 원인은 이해 실패가 아니라 **누락**이다. 함수 이름을 지문 용어로 짓고 규칙별로 단독 검증하면 누락이 구조적으로 드러난다 — 테스트 전략의 단위→통합 원리의 시험장 버전.
- **③ 확장 · TRADE-OFF** — 함수 분해는 타이핑이 늘지만(비용) 디버깅 시간을 그 몇 배로 돌려준다. 국내 코테(카카오류)에서 1~2번을 이 유형이 차지하므로, **빠르고 정확한 완주가 곧 2번 문제에 쓸 시간을 버는 것** — 속도 자체가 전략 자원이다.

## 유형 훈련 — Union-Find: "연결이 하나씩 추가되는" 문제

> 백로그 7번 (출제 대비). 실습 문제: 친구 네트워크 (연결될 때마다 무리 크기 출력).
> **난이도**: 프로그래머스 **Lv2~3** · 기업 2~3번.
> 진행: **🤔 생각 → 📖 읽기 → ✅ 확인** 순서.

---

### 0단계. 판별 — BFS와의 갈림길

| 지문 신호 | 판단 |
|---|---|
| 그래프가 **고정**돼 있고 덩어리를 세라 | [BFS/DFS](e4-pattern-drills.md)로 충분 |
| **간선이 하나씩 추가되면서** 그때마다 "같은 그룹인가?"/"그룹 크기는?" 질의 | **Union-Find** — 매번 BFS를 다시 돌리면 O(질의×n) 낭비 |
| "사이클이 생기는 순간을 찾아라" | Union-Find (같은 루트끼리 union 시도 = 사이클) |

> 판별 한 줄: **그래프가 "자라나는 중"에 질의가 끼어들면 Union-Find다.**

---

### 1단계. 🤔 생각 — 왜 "대표(루트)"만 관리하면 되나?

<details><summary>📖 추론 열기</summary>

"같은 그룹인가?"에 필요한 건 구성원 목록이 아니라 **그룹의 신분증 하나**다. 각 원소가 부모를 가리키게 하고, 뿌리(대표)가 같으면 같은 그룹 — 집합 비교를 **대표 비교로 축소**한 것이다.

빠르게 만드는 최적화 2개: **경로 압축**(find 하며 만난 노드를 전부 루트 직결로) + **크기 기준 병합**(작은 트리를 큰 트리 밑으로). 둘을 합치면 연산당 사실상 O(1) (역아커만 α).

</details>

**✅ 확인**: 압축 없이 1-2-3-…-n 사슬로 union하면 find가 O(n) — 최적화가 장식이 아닌 이유.

---

### 2단계. 결론 — 템플릿 (Java)

```java
static int[] parent, size;

static void init(int n) {
    parent = new int[n]; size = new int[n];
    for (int i = 0; i < n; i++) { parent[i] = i; size[i] = 1; }
}
static int find(int x) {
    if (parent[x] == x) return x;
    return parent[x] = find(parent[x]);        // ★ 경로 압축 — 대입이 핵심
}
static int union(int a, int b) {               // 병합 후 그룹 크기 반환
    int ra = find(a), rb = find(b);
    if (ra == rb) return size[ra];             // 이미 같은 그룹 (사이클 판정 지점)
    if (size[ra] < size[rb]) { int t = ra; ra = rb; rb = t; }
    parent[rb] = ra;                           // 작은 쪽을 큰 쪽 밑으로
    size[ra] += size[rb];
    return size[ra];
}
```

### 3단계. ✅ 확인 + 함정

union(1,2)→2, union(3,4)→2, union(2,3)→**4** — 손으로 트리 그려 검증.

- [ ] `parent[x] = find(...)` **대입**을 빼먹으면 압축이 안 됨 (동작은 하지만 느려짐 — 숨은 시간초과)
- [ ] 이름이 문자열로 오면 `HashMap<String,Integer>`로 번호 매핑부터
- [ ] size는 **루트에서만 유효** — 반드시 find 후 조회
- [ ] 노드 수를 모르면 배열 대신 Map 기반, 또는 등장 시점에 init

### 3단 요약 (암기)

- **① 결론 · WHAT** — 자라나는 그래프의 그룹 질의는 Union-Find: find(대표 조회)+union(병합), 경로 압축+크기 병합으로 연산당 사실상 O(1).
- **② 원리 · HOW** — 집합 비교를 **대표 비교로 축소**한 구조. 같은 루트에 union 시도 = 사이클 발견이라는 부수 효과가 크루스칼 MST의 심장이기도 하다.
- **③ 확장 · TRADE-OFF** — 못 하는 것: **분리(un-union)와 경로 자체 복원** — 그게 필요하면 다른 도구다. 고정 그래프 한 번 질의면 BFS가 더 단순하다는 판별을 잊지 말 것.
