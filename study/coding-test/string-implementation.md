# 유형 훈련 — 카카오식 문자열 구현: 알고리즘 없는 체력전

> 백로그 9번 (국내 기업 특화). 대표: 문자열 압축·다트 게임·파일명 정렬류.
> **난이도**: 프로그래머스 **Lv1~2** · 기업 1~2번 — 알고리즘 지식 0으로 풀리지만 **명세 한 줄 누락이 곧 오답**인 유형. [REST API 기출](rest-api-pagination.md)과 같은 "꼼꼼함 시험" 계열.
> 진행: **🤔 생각 → 📖 읽기 → ✅ 확인** 순서.

## 0단계. 판별 — 지문 신호

| 지문 신호 | 판단 |
|---|---|
| 지문이 **길고** 규칙이 여러 개인데 자료구조 힌트가 없다 | 구현 문제 — 알고리즘 찾느라 시간 쓰지 말 것 |
| "규칙에 따라 변환/시뮬레이션하라" | 구현 확정 |
| 입력 크기가 작다 (n ≤ 1,000) | **복잡도 걱정 불필요 = 정확성 승부**라는 출제자 신호 |

> 판별 한 줄: **지문이 길고 입력이 작으면, 시험 대상은 머리가 아니라 꼼꼼함이다.** 이 순간 전략을 "좋은 알고리즘 찾기"에서 "명세 빠짐없이 옮기기"로 전환한다.

## 1단계. 🤔 생각 — 긴 지문을 어떻게 코드로 안전하게 옮기나?

<details><summary>📖 추론 열기</summary>

한 덩어리 main에 다 쓰면 명세 누락을 눈으로 못 찾는다. 전략은 **명세 문장 : 함수 = 1 : 1 분해**:

```
지문의 규칙 ①②③  →  rule1(), rule2(), rule3()  →  각각 예제로 단독 검증  →  조립
```

- 함수 이름을 **지문의 용어 그대로** — "보너스 점수" 규칙이면 `applyBonus()`. 나중에 지문과 코드를 나란히 놓고 대조 가능
- **예제 입출력을 단계별 중간값까지 손으로** 먼저 계산해 두고, 함수 하나 만들 때마다 그 중간값과 대조 — 다 만들고 최종 출력만 비교하면 어느 규칙이 틀렸는지 못 찾는다

> [테스트 전략 노트](../lang/java/deep-testing-strategy.md)의 축소판이다 — 단위(규칙별 함수) 검증 후 통합. 시험장에서도 같은 근육.

</details>

**✅ 확인**: 자신의 최근 구현 문제 오답을 복기 — 대부분 "규칙을 잘못 이해"가 아니라 **"규칙 하나를 안 읽음"**이었을 것. 그래서 해법이 알고리즘이 아니라 절차다.

## 2단계. 결론 — 자주 쓰는 파싱 관용구 (Java)

```java
// 숫자·문자 혼합 파싱 (다트게임류): 인덱스 포인터 하나로 훑기
int i = 0;
while (i < s.length()) {
    int start = i;
    while (i < s.length() && Character.isDigit(s.charAt(i))) i++;   // 숫자 구간
    int num = Integer.parseInt(s.substring(start, i));
    char option = s.charAt(i++);                                    // 뒤따르는 기호
    // ... 규칙 적용 ...
}

// 압축류: 길이 k 단위로 자르며 연속 반복 세기
for (int k = 1; k <= s.length() / 2; k++) { /* 단위 k 시도 */ }

// 구분자 파싱: split보다 지문 규칙이 복잡하면 수동 substring이 안전
// (연속 구분자·빈 토큰 처리를 split의 암묵 규칙에 맡기지 말 것)
```

**전역 체크 습관**: 대소문자 구분, 빈 문자열, 경계(마지막 토큰 뒤 구분자 유무), `Integer.parseInt`의 앞자리 0 — 전부 지문에 답이 있다. **모르면 추측 말고 지문을 다시 읽는다.**

## 3단계. 함정 체크리스트

- [ ] 명세 문장마다 **구현했는지 체크 표시**하며 옮겼나 (지문에 연필로 ✓)
- [ ] 예제의 **중간 단계 값**을 손으로 계산해 두고 함수 단위로 대조했나
- [ ] 엣지: 빈 입력·규칙이 한 번도 발동 안 하는 입력·전부 같은 문자
- [ ] `split` 암묵 규칙(끝 빈 토큰 제거 등)에 당하지 않았나 — 복잡하면 수동 파싱
- [ ] 입력이 작다고 확인했나 — 크면 이 유형이 아니라 알고리즘 문제다 (판별 재검토)

## 3단 요약 (암기)

- **① 결론 · WHAT** — 지문 길고 입력 작으면 구현 체력전: 전략을 "알고리즘 찾기"에서 **"명세 문장:함수 = 1:1 옮기기 + 중간값 대조"**로 전환한다.
- **② 원리 · HOW** — 이 유형의 오답 원인은 이해 실패가 아니라 **누락**이다. 함수 이름을 지문 용어로 짓고 규칙별로 단독 검증하면 누락이 구조적으로 드러난다 — 테스트 전략의 단위→통합 원리의 시험장 버전.
- **③ 확장 · TRADE-OFF** — 함수 분해는 타이핑이 늘지만(비용) 디버깅 시간을 그 몇 배로 돌려준다. 국내 코테(카카오류)에서 1~2번을 이 유형이 차지하므로, **빠르고 정확한 완주가 곧 2번 문제에 쓸 시간을 버는 것** — 속도 자체가 전략 자원이다.
