# 유형 훈련 — 그리디: "왜 이 정렬이 최적인가"를 한 줄로

> 백로그 4번 — [로드맵 D10](../coding-test-2week.md)의 실전판. 실습 문제: 회의실 배정 (프로그래머스/백준 1931 동형).
> **난이도**: 프로그래머스 **Lv2** · 기업 2번(중) — 코드는 5줄인데 **증명을 못 하면 틀린 정렬 기준을 골라 전멸**하는 유형.
> 진행: **🤔 생각 → 📖 읽기 → ✅ 확인** 순서.

## 0단계. 판별 — 지문 신호

| 지문 신호 | 판단 |
|---|---|
| "최대 **개수**를 선택하라" (겹치지 않게) | 그리디 후보 ⭕ |
| 정렬하고 앞에서부터 취하면 될 것 같은 직감 | 후보 ⭕ — 단 **증명 전엔 확정 금지** |
| 지금의 선택이 **미래의 용량/기회를 소모**한다 (배낭처럼) | ❌ 그리디 실패 신호 → DP로 |
| 부분 문제의 답을 **되돌릴 일이 없다** | 그리디 성립 방향 |

> 판별 한 줄: **"욕심내도 나중에 후회가 없음"을 증명할 수 있을 때만 그리디다.** 증명 도구가 이 드릴의 본체인 교환 논증(exchange argument).

## 1단계. 🤔 생각 — 회의실 배정, 무엇으로 정렬하나?

*(회의 [시작,끝] n개, 겹치지 않게 최대 개수. 후보: ① 시작 빠른 순 ② 짧은 순 ③ 끝나는 순. 각각 반례를 만들어 보라.)*

<details><summary>📖 추론 열기</summary>

**① 시작 순 반례**: `[1,100], [2,3], [4,5]` — 시작 빠른 [1,100]을 잡으면 1개, 답은 2개.
**② 짧은 순 반례**: `[1,10], [9,12], [11,20]` — 가장 짧은 [9,12]를 잡으면 1개, 답은 2개 ([1,10]+[11,20]).
**③ 끝나는 순** — 반례가 안 만들어진다. 왜인지가 핵심:

> **교환 논증**: 어떤 최적해가 있다고 하자. 그 최적해의 첫 회의를 "가장 일찍 끝나는 회의"로 **바꿔치기**해도 — 더 일찍 끝나니 뒤의 모든 회의는 그대로 유효하다. 즉 **손해가 없다.** 같은 논리를 두 번째, 세 번째에 반복하면: "끝나는 순 그리디 해"는 어떤 최적해와도 개수가 같다. ∎

이게 그리디 증명의 표준 틀이다: **"최적해를 내 선택으로 한 조각씩 교환해도 나빠지지 않음"**을 보인다. 시험장에선 엄밀 증명 대신 이 한 문장 — *"가장 일찍 끝나는 걸 잡는 게 미래의 선택지를 최대로 남긴다"* — 을 말할 수 있으면 된다.

</details>

**✅ 확인**: ①②의 반례를 내 손으로 재현 — **틀린 기준이 왜 틀리는지**를 아는 게 맞는 기준을 외우는 것보다 오래 간다.

---

## 2단계. 결론 — 코드 (Java)

```java
static int maxMeetings(int[][] m) {
    Arrays.sort(m, (a, b) -> a[1] != b[1] ? a[1] - b[1] : a[0] - b[0]);  // 끝나는 시간 순
    int count = 0, lastEnd = Integer.MIN_VALUE;
    for (int[] x : m)
        if (x[0] >= lastEnd) {        // 이전 회의가 끝난 뒤 시작하면
            count++;
            lastEnd = x[1];           // 채택하고 기준 갱신
        }
    return count;
}
```

정렬 O(n log n) + 한 번 순회 — 그리디의 전형적 모양: **정렬이 알고리즘의 전부이고, 루프는 확인일 뿐.**

## 3단계. ✅ 전체 확인 — 손 추적

회의 `[1,4] [3,5] [0,6] [5,7] [8,9] [5,9]` → 끝 시간 정렬: `[1,4] [3,5] [0,6] [5,7] [5,9] [8,9]`

| 회의 | 시작 ≥ lastEnd? | 채택 | lastEnd |
|---|---|---|---|
| [1,4] | ✓ | 1 | 4 |
| [3,5] | `3 < 4` ✗ | — | 4 |
| [0,6] | ✗ | — | 4 |
| [5,7] | 5 ≥ 4 ✓ | 2 | 7 |
| [5,9] | ✗ | — | 7 |
| [8,9] | 8 ≥ 7 ✓ | **3** | 9 |

**답: 3**

## 4단계. 함정 체크리스트

- [ ] **"끝나는 시간이 같으면 시작 순" 2차 정렬** — `[2,2]`처럼 시작=끝인 회의가 섞이면 순서에 따라 답이 달라질 수 있음
- [ ] 경계: "끝나는 순간 시작" 허용 여부 (`>=` vs `>`) — 지문 확인
- [ ] **그리디 실패 신호를 놓치지 않았나** — 선택이 무게/용량을 소모하면(0/1 배낭) 그리디 반례 존재 → [DP 테이블 드릴](dp-table-knapsack.md)
- [ ] 최소 회의실 **개수**를 묻는 변형은 다른 문제 (시작·끝 이벤트 스위프 or 힙 — [힙 드릴](priority-queue-heap.md))

## 3단 요약 (암기)

- **① 결론 · WHAT** — 그리디는 "정렬 기준 선택 + 그 기준이 최적인 이유 한 줄"이 전부다. 회의실 배정은 **끝나는 시간 순** — "가장 일찍 끝나는 걸 잡아야 미래 선택지가 최대"이기 때문.
- **② 원리 · HOW** — 증명 틀은 **교환 논증**: 임의의 최적해에서 첫 선택을 내 그리디 선택으로 바꿔도 손해가 없음을 보이고 귀납 반복. 시험장 버전은 "바꿔치기해도 안 나빠진다" 한 문장.
- **③ 확장 · TRADE-OFF** — 그리디의 위험은 **그럴듯한데 틀린 기준**이다(시작 순·짧은 순 반례). 판별법: 반례를 30초 못 만들겠으면 교환 논증을 시도하고, 선택이 미래 자원을 소모하는 구조(배낭)면 미련 없이 DP로 — 그리디와 DP의 경계 감각 자체가 이 유형의 득점 포인트다.
