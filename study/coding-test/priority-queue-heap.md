## 0단계. 판별 — 지문 신호

| 지문 신호 | 판단 |
|---|---|
| "**가장 작은/큰 것을 꺼내 → 가공 → 다시 넣기**를 반복" | 힙 확정 (이 드릴의 본체) |
| "K번째로 큰/작은 값" (스트림으로 들어옴) | 크기 K 힙 유지 |
| 반복문 안에서 `sort()`를 또 부르고 싶어진다 | **그 충동이 곧 힙 신호** |
| 전체 정렬 결과가 끝까지 필요 | 힙 아님 — 그냥 한 번 정렬 |

> 판별 한 줄: **전체 순서는 필요 없고 "다음 하나"만 계속 필요하면 힙이다.**

## 1단계. 🤔 생각 — 매번 정렬하면 왜 안 되나?

*(원소를 꺼내고 새 원소를 넣을 때마다 `Collections.sort()`를 다시 부르면? 복잡도를 계산해 보라.)*

<details><summary>📖 추론 열기</summary>

n개 원소에 n번의 갱신이 일어나면 매번 정렬은 **O(n × n log n)** — 10⁵개면 시간 초과 확정. 낭비의 정체는:

> 정렬은 **전체 순서**를 만드는데, 우리가 쓰는 건 매번 **맨 앞 하나**뿐이다. 필요한 것보다 훨씬 강한 것을 계산하고 있다.

힙은 "최솟값이 루트에 있다"는 **느슨한 순서만** 유지한다 — 그래서 꺼내기·넣기가 O(log n), 전체 O(n log n). ([이진 조합](binary-distinct-combinations.md)의 "필요한 것만 계산하라"와 같은 절약 원리다.)

</details>

**✅ 확인**: Java에서 `PriorityQueue`의 `peek()`은 O(1), `poll()`/`offer()`는 O(log n) — 그리고 **최대힙은 생성자에 `Comparator.reverseOrder()`** (기본이 최소힙이라는 것, 시험장 1분 함정).

## 2단계. 결론 — Jesse and Cookies (Java)

> 문제: 과자들의 단맛 배열. **가장 안 단 과자 둘을 꺼내** `새 과자 = 1번째 + 2×2번째`로 합치는 연산을, 모든 과자가 K 이상이 될 때까지 반복. 최소 연산 횟수는? (불가능하면 -1)

```java
static int cookies(int k, int[] a) {
    PriorityQueue<Long> pq = new PriorityQueue<>();          // 기본 = 최소힙
    for (int x : a) pq.offer((long) x);
    int ops = 0;
    while (pq.peek() < k) {                                  // 아직 목표 미달
        if (pq.size() < 2) return -1;                        // ★ 합칠 게 없음 = 불가능
        long first = pq.poll(), second = pq.poll();
        pq.offer(first + 2 * second);
        ops++;
    }
    return ops;
}
```

| 1 | 1, 2 | 1+2×2=**5** | [3,5,9,10,12] | 3 ✗ |
| 2 | 3, 5 | 3+2×5=**13** | [9,10,12,13] | 9 ✓ |

## 4단계. 함정 체크리스트

- [ ] **원소 1개 남았는데 목표 미달** → `size() < 2` 검사 없이 poll 두 번 하면 NPE. -1 반환 조건
- [ ] 합성값은 **long** — 단맛이 커지면 int 초과
- [ ] 최대힙 필요할 때 `new PriorityQueue<>(Comparator.reverseOrder())` — 기본은 최소힙
- [ ] `peek()`으로 검사, `poll()`로 제거 — peek 자리에 poll 쓰면 원소가 증발
- [ ] "K번째" 변형: **크기 K를 유지하는 반대 방향 힙** (K번째로 큰 값 = 크기 K 최소힙의 루트)

## 3단 요약 (암기)

- **① 결론 · WHAT** — "매번 최솟값(최댓값)을 꺼내 가공 후 재삽입"이 반복되면 힙. 반복문 안에서 sort를 또 부르고 싶은 충동이 곧 판별 신호다.
- **② 원리 · HOW** — 정렬은 전체 순서(과잉), 힙은 "루트가 최솟값"이라는 느슨한 순서만 유지해 poll/offer O(log n). 필요한 만큼만 계산하는 절약이 O(n²log n)→O(n log n)을 만든다.
- **③ 확장 · TRADE-OFF** — 힙은 **중간 원소 탐색·삭제가 O(n)** — 그게 필요하면 TreeMap. "K번째" 스트림은 크기 K 역방향 힙, 두 힙(최대+최소)을 맞붙이면 중앙값 스트림까지 커버 — 전부 이 템플릿의 변주다.
