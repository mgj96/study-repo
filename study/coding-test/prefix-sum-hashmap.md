## 1단계. 🤔 생각 — 음수가 섞이면 윈도우는 왜 죽나?

*(윈도우가 성립하려면 "창을 늘리면 합이 커지고, 줄이면 작아진다"가 필요하다. 음수가 있으면?)*

<details><summary>📖 추론 열기</summary>

윈도우의 엔진은 **단조성**이다: 합이 크면 왼쪽을 당기고, 작으면 오른쪽을 늘린다 — 이 판단은 "늘리면 커진다"가 보장될 때만 유효하다. 음수가 섞이면 **창을 늘렸는데 합이 줄어들 수 있어** 어느 쪽으로 움직일지 판단 근거가 사라진다.

> [파라메트릭 이분탐색](parametric-binary-search.md)의 성립 조건이 판정의 단조성이었듯, **윈도우의 성립 조건은 창-합의 단조성**이다. 도구마다 "성립 조건"이 있고, 판별이란 그 조건을 검사하는 일이다.

</details>

**✅ 확인**: `[1, -1, 1]`에서 합 1인 창을 윈도우로 쫓아가 보라 — 창을 어떻게 움직여도 [1], [1,-1,1], [1]（뒤） 세 개를 일관된 규칙으로 못 잡는다.

## 2단계. 🤔 생각 — 그럼 무엇으로 바꾸나?

*(구간 합 = 누적합의 차: sum(i..j) = pre[j] - pre[i-1]. "합이 K인 구간의 개수"를 이 식으로 다시 써 보라.)*

<details><summary>📖 추론 열기</summary>

`pre[j] - pre[i] = K`  ⇔  `pre[i] = pre[j] - K`. 그러므로 j를 왼쪽부터 훑으며 —

> **"지금 누적합 − K 값을, 과거에 몇 번 봤는가?"** — 그 횟수가 j에서 끝나는 정답 구간의 개수다. 과거 누적합의 등장 횟수를 HashMap에 쌓으면 O(n).

이는 two-sum의 일반화이자, [Sherlock 드릴](sherlock-and-anagrams.md)의 "쌍을 직접 세지 말고 그룹으로" 사고와 동일하다 — **쌍 (i,j)를 열거하지 않고, j 시점에 '짝이 될 수 있는 i의 개수'를 조회**한다.

</details>

**✅ 확인**: 왜 map에 `{0: 1}`을 미리 넣어야 하나? — `pre[j] = K`인 순간(배열 처음부터 j까지가 정답 구간)에 `pre[j]-K = 0`을 찾게 되는데, "아무것도 안 더한 상태"도 한 번 등장한 누적합이기 때문. 이 초기값 누락이 이 유형 오답 1위다.

---

## 3단계. 결론 — 코드 (Java)

```java
static long countSubarrays(int[] a, long k) {
    Map<Long, Integer> seen = new HashMap<>();
    seen.put(0L, 1);                          // ★ 빈 접두사 — 처음부터 시작하는 구간용
    long pre = 0, count = 0;
    for (int x : a) {
        pre += x;
        count += seen.getOrDefault(pre - k, 0);   // 짝이 되는 과거 누적합 조회
        seen.merge(pre, 1, Integer::sum);         // 지금 누적합을 과거 목록에 등록
    }
    return count;
}
```

조회가 등록보다 **먼저**다 — 순서를 바꾸면 K=0일 때 자기 자신과 짝지어 오답.

## 4단계. ✅ 전체 확인 — a=[1,2,3], K=3 손 추적

| x | pre | pre−K 조회 | count | map 등록 후 |
|---|---|---|---|---|
| — | 0 | — | 0 | {0:1} |
| 1 | 1 | −2 → 0회 | 0 | {0:1, 1:1} |
| 2 | 3 | 0 → **1회** | 1 | {0:1, 1:1, 3:1} |
| 3 | 6 | 3 → **1회** | **2** | {…, 6:1} |

**답: 2** — 구간 [1,2]와 [3] ✓

## 5단계. 함정 체크리스트

- [ ] **`seen.put(0L, 1)` 초기값** — 누락하면 "처음부터 시작하는 구간"이 전부 빠짐 (오답 1위)
- [ ] **조회 → 등록 순서** — 바꾸면 K=0에서 자기 매칭
- [ ] 누적합·개수는 **long** (10⁵개 × 10⁹ 값)
- [ ] "개수"가 아니라 "**최장 길이**"를 묻는 변형 → map에 개수 대신 **최초 등장 인덱스** 저장
- [ ] 전부 양수라고 명시돼 있으면 윈도우도 정답 — 더 익숙한 쪽으로 (판별표 참조)

## 3단 요약 (암기)

- **① 결론 · WHAT** — 음수 섞인 "합이 K인 연속 구간"은 윈도우가 아니라 **누적합+해시**: `pre−K`를 과거에 본 횟수를 세면 O(n).
- **② 원리 · HOW** — 윈도우의 성립 조건(창-합 단조성)이 음수에서 깨지므로, 구간 합을 **누적합의 차**로 바꿔 "쌍 열거"를 "과거 조회"로 치환한다. `{0:1}` 초기값은 빈 접두사의 등장을 의미한다.
- **③ 확장 · TRADE-OFF** — 같은 틀로 "합이 K의 배수인 구간"(누적합을 mod로 저장), "0과 1 개수가 같은 구간"(0을 −1로 치환) 등이 전부 풀린다. 대가는 HashMap 메모리 O(n) — 그리고 이 유형의 진짜 시험은 코드가 아니라 **윈도우/누적합 판별을 30초 안에 끝내는 것**이다.
