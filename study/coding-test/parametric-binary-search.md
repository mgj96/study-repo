## 1단계. 🤔 생각 — 왜 "직접 계산"이 막히고, 뒤집으면 뚫리나?

*(위 기계 문제에서 최소 일수를 바로 구하는 식을 세워 보라. 잘 안 될 것이다. 그런데 "d일이면 목표를 채우나?"는?)*

<details><summary>📖 추론 열기</summary>

정방향("최소 일수 = ?")은 기계마다 주기가 달라 닫힌 식이 없다. 그런데 역방향은 허무할 만큼 쉽다:

```
d일 동안의 총 생산량 = Σ (d / a[i])     ← O(n) 한 줄
가능(d) = (총 생산량 >= goal)
```

그리고 이 판정은 **단조**다 — d일에 가능하면 d+1일엔 당연히 가능. 즉 수직선이 이렇게 생겼다:

```
d:        1  2  3  4  5  6  7  8 ...
가능?     ✗  ✗  ✗  ✓  ✓  ✓  ✓  ✓
                   ↑ 이 경계가 답 — "정렬된 것"은 배열이 아니라 이 ✗✗✗✓✓✓ 구조다
```

✗✗✗✓✓✓에서 경계 찾기 = 이분탐색. **어려운 최적화 문제가 "쉬운 판정 문제 × log번"으로 분해**된 것이다.

> [이진 조합 드릴](binary-distinct-combinations.md)의 "만들지 말고 세라", [REST API 드릴](rest-api-pagination.md)의 "모으고 나서 판단하라"에 이어 — 이 유형의 전환은 **"계산하지 말고 검증하라"**다. 세 드릴이 같은 메타 패턴: 정면돌파가 막히면 문제를 뒤집는다.

</details>

**✅ 확인**: 기계 a=[2,3], goal=5로 가능(d)를 손 계산 — d=6: 6/2+6/3 = 3+2 = 5 ✓ / d=5: 2+1=3 ✗. 경계는 6.

## 2단계. 🤔 생각 — lo/hi 갱신에서 왜 `hi = mid`고 `lo = mid + 1`인가?

*(가능하면 hi=mid, 불가능하면 lo=mid+1. mid-1이나 mid로 안 하는 이유는?)*

<details><summary>📖 추론 열기</summary>

**불변식으로 설계**하면 헷갈리지 않는다: "**답은 항상 [lo, hi] 안에 있다**"를 매 턴 유지한다.

- `가능(mid)` → mid가 답일 **수도** 있다 → 버리면 안 됨 → `hi = mid` (mid 포함 유지)
- `불가능(mid)` → mid는 절대 답이 아님 → `lo = mid + 1` (mid 제외)
- 종료: `lo == hi` — 구간이 한 점으로 줄면 그게 답

```java
long lo = 1, hi = MAX;                    // 답이 반드시 존재하는 범위로 초기화
while (lo < hi) {
    long mid = lo + (hi - lo) / 2;        // (lo+hi)/2는 오버플로 위험
    if (possible(mid)) hi = mid;          // 답 후보 — 포함한 채 좁힘
    else lo = mid + 1;                    // 답 아님 — 확실히 버림
}
return lo;                                // lo == hi == 최솟값
```

"최댓값을 구하라"(반대 방향 ✓✓✓✗✗✗)면 대칭으로 `lo = mid`(가능 시) / `hi = mid - 1`, 이때 `mid = lo + (hi - lo + 1) / 2`로 올림해야 무한 루프가 안 난다.

</details>

**✅ 확인**: 무한 루프 검산 — lo=4, hi=5일 때 mid=4: 가능이면 hi=4(수렴), 불가능이면 lo=5(수렴). 어느 쪽도 구간이 줄었는지 확인.

## 3단계. 결론 — 전체 코드 (Java)

```java
static long minDays(int[] a, long goal) {
    long lo = 1, hi = (long) goal * min(a);          // 상한: 가장 빠른 기계 혼자 다 만드는 시간
    while (lo < hi) {
        long mid = lo + (hi - lo) / 2;
        if (produced(a, mid) >= goal) hi = mid;
        else lo = mid + 1;
    }
    return lo;
}
static long produced(int[] a, long d) {              // 판정 함수 — 이 문제의 진짜 본체
    long sum = 0;
    for (int x : a) {
        sum += d / x;
        if (sum >= Integer.MAX_VALUE) return sum;    // 조기 종료 겸 오버플로 방어
    }
    return sum;
}
```

구조가 항상 같다: **껍데기(이분탐색 7줄)는 복붙, 문제마다 새로 쓰는 건 `possible()` 하나.**

## 5단계. 함정 체크리스트

- [ ] **단조성 확인 없이 적용하지 않았나** — 가능/불가능이 ✗✓✗처럼 오락가락하면 이분탐색 자체가 무효 (이게 성립 조건이다)
- [ ] `mid = lo + (hi - lo) / 2` — `(lo+hi)/2`는 **오버플로**
- [ ] 판정 함수 내부 합계는 **long** (d가 10⁹이면 d/x 합이 int를 순식간에 넘음)
- [ ] 상한(hi) 초기값이 **답을 반드시 포함**하는가 — 애매하면 넉넉히 (log라 비용 미미)
- [ ] 최댓값 버전에서 `mid` **올림** 안 하면 무한 루프
- [ ] 답이 존재하지 않을 수 있는 문제인가 — 종료 후 `possible(lo)` 한 번 더 검증

## 3단 요약 (암기)

- **① 결론 · WHAT** — "~한 최솟값/최댓값"인데 직접 계산식이 없으면 **"답이 x일 때 가능한가?"로 뒤집어라.** 판정이 O(n)·단조면 이분탐색으로 O(n log MAX) — 껍데기는 복붙이고 문제의 본체는 `possible()` 하나다.
- **② 원리 · HOW** — 정렬된 것은 배열이 아니라 **가능/불가능의 ✗✗✗✓✓✓ 경계 구조**다. 루프는 "답은 [lo, hi] 안"이라는 불변식 유지로 설계한다: 가능이면 후보 포함(`hi=mid`), 불가능이면 확실 제외(`lo=mid+1`), 한 점 수렴이 답.
- **③ 확장 · TRADE-OFF** — 성립 조건은 **단조성** — 깨지면 무효라 판별 단계에서 반드시 확인한다. 같은 전환으로 "가장 가까운 정거장 최대 거리", "예산 상한" 류가 전부 풀리며, 판정 함수가 O(n log n)이어도 총합은 여전히 싸다. [격자 BFS](grid-bfs-dfs.md)·[윈도우](longest-unique-substring.md)와 함께 "**불변식으로 루프를 설계한다**"는 공통 근육을 훈련하는 유형이다.
