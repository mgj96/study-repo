# 딥다이브 — 모듈성 이론: 경계는 왜 "그곳"에 그어야 하나

> 기반: **Parnas, *On the Criteria To Be Used in Decomposing Systems into Modules* (CACM 1972)** · **Constantine & Yourdon, *Structured Design* (1974/1979)** · **Page-Jones, *Comparing Techniques by Means of Encapsulation and Connascence* (OOPSLA 1992)** · **Martin, *OO Design Quality Metrics* (1994) / *Agile Software Development* (2002)** · **Evans, *Domain-Driven Design* (2003)**
> 형식: 30초 직관 → 논문의 실험 → 원리 → 트레이드오프.
> **선행**: 경계 긋기의 실무 기준 4개는 [concept.md](concept.md) 3-2장. 이 노트는 그 기준들이 **어느 이론에서 나왔는지**를 판다.

## 0. 30초 직관 — 좋은 경계는 "바뀔 것을 숨기는 선"이다

[concept.md](concept.md)에서 경계 긋기 기준 4개(변경 이유·데이터 소유권·트랜잭션·팀)를 봤다. 그런데 **왜 하필 그 기준들인가?** 답은 하나의 문장으로 수렴한다:

> **모듈 경계란 기능을 나누는 선이 아니라, "바뀔 가능성이 있는 설계 결정"을 가두는 벽이다.**

이 문장은 1972년 논문 한 편에서 나왔고(1장), 이후 50년간 세 번 정밀화됐다 — 결합도·응집도라는 **등급표**로(2장), 커너선스라는 **통합 어휘**로(3장), 패키지 메트릭이라는 **숫자**로(4장). 그리고 DDD가 **언어**라는 새 기준을 추가했다(5장).

전부 관통하는 질문은 같다: **"여기를 바꾸면 어디까지 흔들리나?"**

## 1. Parnas (1972) — 상식적인 분해가 지는 실험

### 1-1. 실험 설계

David Parnas는 CACM에 실린 5쪽짜리 논문에서 작은 프로그램(KWIC 색인 — 문장을 회전시켜 정렬하는 색인 생성기) 하나를 **두 가지 방식으로 분해**해 비교했다.

**분해 A — 처리 단계 기준 (당시의 상식)**

```
[입력 읽기] → [행 회전] → [알파벳 정렬] → [출력]
```

작업 흐름도(flowchart)를 따라 단계마다 모듈 하나. **누구나 자연스럽다고 느끼는** 분해다.

**분해 B — 설계 결정 기준 (Parnas의 제안)**

```
[행 저장 방식을 아는 모듈]  [회전 방식을 아는 모듈]  [정렬 방식을 아는 모듈] ...
```

각 모듈이 **"어려웠거나 바뀔 것 같은 설계 결정" 하나씩을 숨긴다(hide).** 예: "문자들을 메모리에 어떻게 저장하나"는 저장 모듈만 알고, 나머지는 인터페이스로만 접근한다.

### 1-2. 결과 — 그리고 이유

겉보기 기능은 동일하다. 차이는 **변경이 왔을 때** 드러난다:

| 변경 요구 | 분해 A (흐름 기준) | 분해 B (결정 은닉) |
|---|---|---|
| 저장 방식을 메모리→디스크로 | **거의 모든 모듈 수정** (다들 저장 형식을 직접 앎) | 저장 모듈 **하나만** |
| 정렬 알고리즘 교체 | 정렬+인접 모듈 수정 | 정렬 모듈 하나만 |

> "우리는 **흐름도로 시스템을 분해하는 습관**을 버려야 한다. 각 모듈은 **어렵거나 바뀔 것 같은 설계 결정을 다른 모듈들로부터 숨기도록** 선택되어야 한다."
> — Parnas (1972), [CACM 15(12)](https://dl.acm.org/doi/10.1145/361598.361623) (요지 정리)

이게 **정보 은닉(information hiding)** 의 원전이다. 핵심 반전: **"자연스러운 분해"(처리 순서)와 "좋은 분해"(변경 격리)는 다르다.** 흐름은 눈에 보이니 따라 나누기 쉽지만, 변경은 흐름 단계가 아니라 **결정 단위**로 온다.

> 💡 **현대어 번역**: `Controller → Service → Repository`는 분해 A(처리 단계)다. 그래서 "요금 정책 변경" 하나가 세 계층을 다 관통한다. [concept.md](concept.md) 3-3의 **기능별 패키지**가 분해 B다 — "요금"이라는 결정을 한 폴더에 가둔다. 55년 전 실험이 지금의 패키지 논쟁을 이미 끝내놨다.
>
> 캡슐화(필드 private)와 혼동 주의 — 캡슐화는 정보 은닉의 **언어 차원 도구**일 뿐이다. getter로 내부 구조를 다 노출하면 필드가 private이어도 **아무것도 숨기지 않은 것**이다.

## 2. 결합도·응집도 — 나쁨의 등급표 (Constantine & Yourdon)

Parnas가 "무엇을 숨겨라"를 줬다면, 같은 시기 Larry Constantine은 **모듈 사이 연결의 나쁨을 등급**으로 만들었다(*Structured Design*, 1974 IBM Systems Journal / 1979 단행본).

### 2-1. 결합도(coupling) — 모듈 **사이**. 낮을수록 좋다

| 등급 (나쁨→좋음) | 무엇 | 예 |
|---|---|---|
| **내용 결합** | 남의 내부를 직접 참조·수정 | 리플렉션으로 private 조작 |
| **공통 결합** | 전역 상태 공유 | 전역 변수, 아무나 쓰는 공용 테이블 |
| **외부 결합** | 외부 형식·프로토콜을 여럿이 직접 앎 | 여러 모듈이 벤더 응답 포맷을 각자 파싱 |
| **제어 결합** | 플래그를 넘겨 남의 **동작 방식**을 지시 | `calculate(order, /*isVip*/ true)` |
| **스탬프 결합** | 필요 이상 큰 구조체를 통째로 전달 | 필드 2개 쓰려고 엔티티 전체 전달 |
| **자료 결합** | 필요한 값만 주고받음 | `calculate(amount, rate)` |

### 2-2. 응집도(cohesion) — 모듈 **안**. 높을수록 좋다

| 등급 (나쁨→좋음) | 무엇 | 예 |
|---|---|---|
| **우연적** | 아무 관계 없는 것들의 집합 | `Utils` 클래스 |
| **논리적** | "종류가 비슷"할 뿐 | 모든 입출력을 모은 모듈 |
| **시간적** | "같은 때 실행"될 뿐 | `init()에서 하는 일들` |
| **절차적 / 통신적 / 순차적** | 순서·데이터로 이어짐 | 파이프라인 단계들 |
| **기능적** | **하나의 목적**을 위해 전부 존재 | 요금 계산 모듈 |

> **두 등급표는 같은 것의 안팎이다.** 관련된 것을 한 모듈에 모으면(응집↑) 모듈 사이에 주고받을 게 줄어든다(결합↓). 반대로 `Utils`·`Common`처럼 우연적 응집 모듈은 모두가 의존하는 **공통 결합의 온상**이 된다.
> 실무 신호: **"공통 모듈이 제일 자주 바뀐다"** 면 응집이 우연적이라는 뜻이다. 진짜 공통(안정된 것)은 자주 안 바뀐다 — 4장의 안정 의존성 원칙으로 이어진다.

## 3. 커너선스 (Page-Jones, 1992) — 결합을 한 단어로 다시 세다

객체지향이 오자 2장의 등급표가 잘 안 맞기 시작했다(상속·다형성·콜백은 어느 칸인가?). Meilir Page-Jones는 OOPSLA 1992에서 **커너선스(connascence, "함께 태어남")** 라는 통합 어휘를 제안했다:

> **두 요소 사이에 커너선스가 있다 = 한쪽을 바꾸면 다른 쪽도 바꿔야 시스템이 올바르다.**

"함께 바뀌어야 하는 정도"로 모든 결합을 다시 정의한 것이다. 종류는 두 축으로 나뉜다:

### 3-1. 정적 (코드만 보고 앎) — 약한 순

| 종류 | 함께 바뀌는 이유 | 예 |
|---|---|---|
| **이름** | 같은 이름을 참조 | 메서드명 바꾸면 호출부도 |
| **타입** | 같은 타입 합의 | 파라미터 타입 변경 |
| **의미** | **값의 뜻을 관례로 공유** | `status = 1`이 "출차"라는 암묵지 |
| **위치** | **순서에 의존** | `new Fee(5000, 3, true)` — 몇 번째가 뭐더라 |
| **알고리즘** | 같은 알고리즘을 양쪽이 구현 | 클라·서버가 같은 해시를 각자 계산 |

### 3-2. 동적 (실행해야 앎) — 전부 정적보다 강하다

| 종류 | 함께 바뀌는 이유 | 예 |
|---|---|---|
| **실행 순서** | A 다음 B여야 함 | `init()` 먼저 안 부르면 NPE |
| **타이밍** | 시간 간격에 의존 | "락 TTL 30초 안에 끝나야 함" |
| **값** | 여러 값이 함께 맞아야 함 | 주문 상태와 결제 상태의 짝 |
| **정체성** | **같은 인스턴스**여야 함 | 반드시 같은 커넥션/트랜잭션 안에서 |

### 3-3. 사용 규칙 — 이 이론의 실전 가치

> 1. **강한 커너선스일수록 좁은 거리 안에** 가둬라 (같은 함수 > 같은 클래스 > 같은 패키지 > … > 다른 서비스 ❌)
> 2. 거리를 못 줄이면 **커너선스를 약한 것으로 바꿔라**

2번이 리팩터링의 이론적 정의다:

```java
new Fee(5000, 3, true);                     // 위치 커너선스 (강함)
Fee.builder().amount(5000).hours(3)
   .weekend(true).build();                  // → 이름 커너선스 (약함)

if (status == 1) ...                        // 의미 커너선스
if (status == Status.EXITED) ...            // → 이름 커너선스
```

> **분산 시스템 노트들과 정확히 접속한다**: 서비스를 쪼갠다 = 거리를 최대로 늘린다. 그때 남아 있는 **값 커너선스**(두 DB의 상태가 짝이 맞아야 함)와 **타이밍 커너선스**(TTL·타임아웃)가 바로 [분산 정합성](../cs/deep-distributed-consistency.md)과 [Redis 락](../cs/deep-redis-cache-and-lock.md)에서 싸운 그 문제들이다. **"강한 커너선스를 서비스 경계 너머에 두지 마라"** — 트랜잭션이 필요한 둘을 쪼개지 말라는 [concept.md](concept.md) 기준 ③의 이론적 일반화가 이것이다.

## 4. 숫자로 재기 — Martin의 패키지 메트릭

Robert Martin(1994)은 패키지 수준 의존성을 **측정 가능한 수**로 만들었다.

### 4-1. 세 수치

**불안정성(Instability)** — 나가는 의존이 많을수록 흔들리기 쉽다:

$$I = \frac{Ce}{Ca + Ce}$$

($Ca$ = 나를 의존하는 패키지 수, $Ce$ = 내가 의존하는 패키지 수. $I=0$ 최안정, $I=1$ 최불안정)

**추상도(Abstractness)** — $A$ = 추상 타입 비율 (0 = 전부 구체, 1 = 전부 추상)

**주계열 거리(Distance from Main Sequence)**:

$$D = |A + I - 1|$$

### 4-2. 두 원칙과 두 지옥

- **안정 의존성 원칙(SDP)**: 의존은 **더 안정된 쪽으로만** 향해야 한다. 자주 바뀌는 것이 안정된 것에 의존해야지, 역방향이면 변경이 상류로 번진다.
- **안정 추상화 원칙(SAP)**: **안정될수록 추상적이어야** 한다. 모두가 의존하는데 구체적이면, 바꿀 수도 없고 확장할 수도 없다.

$D$가 큰 두 구석에는 이름이 있다:

| 구석 | 상태 | 이름 |
|---|---|---|
| $A=0, I=0$ | 구체적인데 모두가 의존 | **고통의 지대(Zone of Pain)** — 바꾸면 전부 깨지는 구체 클래스. 공용 `Utils`·거대 엔티티가 여기 |
| $A=1, I=1$ | 추상적인데 아무도 안 씀 | **무용의 지대(Zone of Uselessness)** — 미래를 위해 만든 인터페이스들 |

> **헥사고날([concept.md](concept.md) 2-2)이 왜 그 모양인지가 여기서 증명된다.** 도메인은 모두가 의존하므로 안정($I \approx 0$)해야 하고, SAP에 따라 **추상적(포트 = 인터페이스)** 이어야 한다. 인프라는 아무도 의존 안 하므로 불안정해도 되고 구체여도 된다. "의존성은 도메인을 향한다"는 구호가 아니라 **SDP+SAP의 따름정리**다. ArchUnit이 검사하는 게 정확히 이 방향이다.

## 5. DDD — 언어가 경계다 (Evans, 2003)

앞의 이론들은 전부 **구조**(의존·변경)로 경계를 판단한다. Eric Evans의 *Domain-Driven Design*(2003)은 다섯 번째 기준을 추가했다: **말**.

### 5-1. 바운디드 컨텍스트

같은 단어가 문맥마다 다른 모델이다:

| "차량"이라는 단어 | 뜻하는 것 |
|---|---|
| **관제** 컨텍스트에서 | 지금 어느 면에 있고 입출차 상태가 뭔지 |
| **정산** 컨텍스트에서 | 요금제·미납액·결제 수단이 붙은 청구 대상 |
| **회원** 컨텍스트에서 | 소유자·등록증·정기권 계약 |

이 셋을 "하나의 Car 엔티티"로 통합하면? **모든 컨텍스트의 변경 이유를 다 짊어진 거대 클래스**가 된다 — 4장의 고통의 지대 그 자체다. DDD의 처방:

> **모델은 컨텍스트 안에서만 유효하다. 경계는 "같은 단어가 다른 뜻이 되는 지점"에 그어라.**
> 그 경계 안에서는 코드·대화·문서가 **하나의 언어(ubiquitous language)** 를 쓴다.

### 5-2. 컨텍스트 사이 — 매핑 패턴

경계를 그었으면 사이 관계를 명시한다. 대표 세 가지:

| 패턴 | 관계 | 예 |
|---|---|---|
| **고객-공급자** | 하류가 상류에 요구사항을 낼 수 있음 | 정산팀이 관제팀에 이벤트 스펙 요청 |
| **순응자(Conformist)** | 하류가 상류 모델을 그냥 따름 | 외부 표준 API를 그대로 수용 |
| **부패 방지 계층(ACL)** | 하류가 **번역 계층**을 두고 자기 모델을 지킴 | 벤더 응답을 내 도메인 모델로 변환하는 어댑터 |

> ACL은 3장의 언어로 "외부와의 커너선스를 번역 계층 한 곳에 가두는 것"이고, 헥사고날의 어댑터가 하는 일이 정확히 이것이다. 이론들이 서로 다른 시대에 같은 답을 낸 셈이다.

## 6. 종합 — 실무 기준 4개의 이론적 뿌리

[concept.md](concept.md) 3-2의 기준들이 어디서 왔는지 이제 답할 수 있다:

| 실무 기준 | 뿌리 이론 |
|---|---|
| ① 같은 이유로 바뀌는가 | **Parnas 정보 은닉** (변경 결정 단위로 나눔) + 응집도 (기능적 응집) |
| ② 데이터를 쓰는 주체가 하나인가 | **DDD 바운디드 컨텍스트** (모델의 소유권) + 공통 결합 회피 |
| ③ 한 트랜잭션에 묶이는가 | **커너선스 규칙** (강한 동적 커너선스는 좁은 거리에) |
| ④ 팀이 다른 주기로 배포하는가 | **콘웨이 법칙** ([concept.md](concept.md) 3-1 · [AI 시대 확장](deep-conway-and-ai-agents.md)) |
| (+) 의존 방향 검사 (ArchUnit) | **Martin SDP/SAP** (의존은 안정·추상 쪽으로) |

> **한 줄 통합**: 기준이 다섯 개처럼 보이지만 전부 한 질문의 다른 각도다 —
> **"여기를 바꾸면 어디까지 흔들리는가, 그 파문이 경계를 넘는가?"**

## 7. 3단 요약 (암기용)

### Q1. 모듈은 무엇을 기준으로 나누나?

- **① 결론 · WHAT** 처리 단계(흐름도)가 아니라 **"바뀔 것 같은 설계 결정" 단위**로 나눈다. 각 모듈이 결정 하나를 숨기고(정보 은닉), 나머지는 인터페이스로만 접근한다.
- **② 원리 · HOW** Parnas(1972)가 같은 프로그램을 흐름 기준과 결정 은닉 기준으로 각각 분해해 비교했다 — 기능은 동일했지만, 저장 방식 변경 같은 요구가 오자 흐름 기준은 거의 전 모듈이 수정됐고 결정 은닉 기준은 한 모듈로 끝났다. **변경은 처리 단계가 아니라 결정 단위로 오기 때문**이다.
- **③ 확장 · TRADE-OFF** 은닉의 값은 **간접화**다 — 인터페이스·추상화 층이 늘고, 처음 읽는 사람에겐 흐름 기준보다 덜 직관적이다. 또 "무엇이 바뀔지"의 예측이 틀리면 엉뚱한 걸 숨긴 비용만 치른다. 그래서 확실히 변동성 있는 것(외부 연동·정책·저장 방식)부터 숨기는 게 실리적이다. 계층별 vs 기능별 패키지 논쟁은 이 실험의 재방송이다.

### Q2. 결합도를 "낮춰라"는 말을 어떻게 실행 가능하게 만드나?

- **① 결론 · WHAT** **커너선스**로 바꿔 말하면 된다: "한쪽을 바꾸면 다른 쪽도 바꿔야 하는 관계"를 찾아, **강한 것일수록 좁은 거리에 가두고, 못 가두면 약한 종류로 바꾼다.**
- **② 원리 · HOW** 정적(이름·타입·의미·위치·알고리즘)보다 동적(실행 순서·타이밍·값·정체성)이 강하다. 위치→이름(빌더), 의미→이름(enum) 전환이 "약하게 바꾸기"의 전형이고, 리팩터링의 상당수가 이 규칙의 사례다.
- **③ 확장 · TRADE-OFF** 서비스 분리는 **거리를 최대로 늘리는 행위**이므로, 그 경계에 강한 커너선스(같은 트랜잭션이어야 함 = 정체성, 상태 짝 = 값)가 걸쳐 있으면 멱등성·Outbox·Saga의 비용을 전부 치르게 된다. "MSA가 힘들다"의 이론적 정체는 대부분 **강한 커너선스를 먼 거리에 둔 것**이다.

### Q3. "의존성은 도메인을 향한다"는 왜 옳은가?

- **① 결론 · WHAT** 구호가 아니라 **Martin의 두 원칙의 따름정리**다 — 의존은 안정된 쪽으로 향해야 하고(SDP), 안정된 것은 추상적이어야 한다(SAP). 모두가 의존하는 도메인은 안정+추상(포트=인터페이스)일 수밖에 없다.
- **② 원리 · HOW** 불안정성 $I = Ce/(Ca+Ce)$, 추상도 $A$, 주계열 거리 $D=|A+I-1|$로 잰다. $D$가 큰 두 구석이 병목이다 — 구체적인데 모두가 의존하는 **고통의 지대**(공용 Utils·거대 엔티티)와, 추상적인데 아무도 안 쓰는 **무용의 지대**(미래용 인터페이스).
- **③ 확장 · TRADE-OFF** 메트릭은 방향을 알려줄 뿐 목표가 아니다 — $D=0$을 맹목적으로 쫓으면 무용의 인터페이스가 늘어난다(무용의 지대로 이동할 뿐). 실전 순서는 **① 고통의 지대 식별(모두가 의존하는 구체물) ② 거기부터 추상 도입 ③ ArchUnit으로 방향 고정** — 헥사고날을 "전면 도입"이 아니라 아픈 곳부터 점진 적용하는 근거가 이것이다.
