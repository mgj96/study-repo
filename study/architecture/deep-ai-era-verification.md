# AI 시대 엔지니어링 — 병목은 구현에서 검증으로 옮겨갔다

> **이 노트의 관점**: 구현 비용이 급락하면 "코드를 쓰는 능력"의 희소성은 줄고, **"맞는지 판별하는 능력"의 희소성이 커진다.** 이 노트는 그 이동을 세 가지로 풀어 쓴다 — ① 검증 구조 ② AI 사용 방식의 내재화 ③ 구조를 바꾸고 유지하는 순서.
> 형식: ① 결론 → ② 원리 → ③ 트레이드오프. [콘웨이 법칙과 AI 에이전트](deep-conway-and-ai-agents.md)가 "조직 구조" 쪽이라면, 이 노트는 "검증 구조" 쪽이다.

---

## 0. 왜 이 얘기가 나왔나 — pgrust 사례

AI 에이전트로 PostgreSQL을 Rust로 다시 쓴 **pgrust**가 PostgreSQL 18.3 회귀 테스트 스위트(약 46,000 쿼리)를 통과했다고 알려졌다. 이 사례를 다룬 글들이 공통으로 짚는 건 구현이 아니라 **검증의 구조**다.

| 관찰 | 의미 |
|---|---|
| 회귀 테스트 스위트라는 **이미 존재하는 정답(오라클)**이 있었다 | AI가 폭주하지 않게 붙잡아 준 건 프롬프트가 아니라 테스트였다 |
| 공개 러너는 테스트를 직렬로 돌려 실제 병렬 러너와 다르다는 지적 | "통과"의 범위는 **러너가 실제로 잡는 범위까지**다 |
| 속도 향상 수치(트랜잭션 약 50%, 분석 약 300배)는 **미공개 버전 기준이라 미검증** | 검증되지 않은 벤치마크는 주장일 뿐 — 소비자 입장에서 경계 대상 |
| 원본 C 코드를 번역한 것이지 깨끗한 재작성이 아니라는 비판 | "누가 어떻게 만들었나"까지 판별해야 결과를 해석할 수 있다 |

> **출처 주의**: 저자 이름·기간·공개일은 매체마다 서로 어긋난다(예: 약 12주 vs 13일). 이 노트는 어긋난 부분을 사실로 쓰지 않고 **"미확인"으로 둔다.** 이 습관 자체가 아래 2장의 본체다.

한 줄 교훈: **저품질 AI 산출물이 넘쳐난다고 같은 수준에 머물 필요는 없다.** 충분히 검증하는 재작성은 원본의 버그까지 발견하는 가치를 남길 수 있고, 반대로 구현 능력이 올라가도 **검증 능력이 같이 따라오지는 않는다.** 그래서 도전 범위를 넓히는 조건은 "결과를 판별할 전문성과 테스트 구조"다.

## 1. 병목 이동 — 생산자는 싸졌고 소비자(검증)는 그대로다

[Little's Law](../cs/deep-performance-engineering.md) 감각으로 보면 간단하다. 요청(=AI가 만든 변경)이 들어오는 속도는 폭증했는데, 처리(=사람의 리뷰·검증) 속도는 그대로면 **대기열이 길어진다.** 대기열이 길어진다는 건 "검증되지 않은 코드가 쌓인다"는 뜻이다.

| | 예전 | 지금 |
|---|---|---|
| 희소 자원 | 구현 시간 | **판별 시간 (리뷰·검증)** |
| 병목 신호 | 일정이 밀린다 | **리뷰 큐가 밀린다 / 검증 없이 머지된다** |
| 처방 | 구현 인력·도구 | **검증을 자동화·구조화** — 테스트, 정적 분석, 측정 |

**Java 번역**: 구현이 싸진 세계에서 사람의 일은 `compile`이 아니라 **`assertEquals`를 설계하는 일**이다. 코드가 "그럴듯하게 돌아간다"와 "명세대로 돌아간다" 사이의 간격을 메우는 건 오직 테스트의 기대값이다.

## 2. 검증 구조의 3층

### 2.1 오라클 — 비교할 정답이 있는가

- 가장 강한 검증은 **이미 신뢰하는 구현·스위트와의 대조**다 (pgrust의 회귀 스위트, 레거시 시스템의 현재 출력).
- 정답이 없는 신규 기능은 **속성(property)**으로 쓴다: "정렬 결과는 입력의 순열이고 오름차순이다" 같은 불변식. ([품질 게이트 — 속성 기반 테스트 계층](../lang/java/quality-gates-and-standards.md))

### 2.2 고정 후 변경 — 현재 동작을 먼저 박제한다

레거시를 건드리기 전에 **지금 동작을 테스트로 고정**(특성화 테스트)하면, 이후 변경은 "의도한 변화"와 "의도치 않은 회귀"로 기계적으로 갈린다. 순서가 핵심이다: **고정 → 변경 → 재확인.** AI가 코드를 대량 수정하는 상황에서 이 순서는 선택이 아니라 안전벨트다.

### 2.3 측정 — 주장과 증거를 분리한다

- 성능 주장은 **같은 조건·같은 부하·반복 측정**이 있어야 증거가 된다 ([성능 공학](../cs/deep-performance-engineering.md): 평균이 아닌 p99, 측정 먼저).
- 그리고 [확률통계 노트](../math/probability-statistics-essentials.md)의 질문을 던진다: **"그 숫자는 어떤 분포 가정 위에 있나?"** 미공개 버전 수치, 조건이 다른 비교는 여기서 걸러진다.
- 기록 습관: **"확인한 것 / 확인하지 못한 것"을 나눠 적는다.** 확인하지 못한 것이 사실처럼 문서에 섞이는 순간, 그 문서는 신뢰를 잃는다.

## 3. AI 사용의 내재화 — 개인 요령에서 팀 기준으로

AI 도구는 빠르게 바뀐다. **도구에 종속된 요령은 도구가 바뀌면 사라지고, 문서로 고정된 기준은 남는다.**

| 층 | 내용 | 이 저장소의 실례 |
|---|---|---|
| 규칙 파일 | 프로젝트 맥락·빌드 명령·금기를 파일로 | `CLAUDE.md`, `HANDOVER.md`를 먼저 읽게 함 |
| 프롬프트 방식 | 작업 단위·출력 형식·근거 요구를 문서화 | 노트 형식 표준(`CONVENTIONS`), 3단 구조 |
| 검증 절차 | AI 산출물이 통과해야 할 관문 | 빌드 → 푸시 → **라이브 페이지로 렌더링 확인** |
| 안전 규칙 | 넣으면 안 되는 것 | 개인정보·소속 정보는 공개 저장소 금지, 사내 코드는 학습에 쓰이는 무료 티어 금지 |

> 판별 질문: **"도구를 바꿔도 같은 품질이 나오는가?"** 아니라면 그건 기준이 아니라 개인 감각이다.

### 3.1 출처부터 찾는 학습

새 기술을 익힐 때의 순서: **공식 문서·원본 구현 → 확인한 것과 못 한 것의 구분 기록 → 그다음에 적용.** 2차 요약(블로그·번역·AI 답변)은 길잡이일 뿐 근거가 아니다. 이 노트가 pgrust 관련 매체 간 불일치를 "미확인"으로 처리한 것이 그 실례다. ([딥다이브 작성 원칙](../writing-guide.md) — 검색·원문 발췌·출처 명시)

## 4. 구조를 바꾸고, 유지한다

AI 시대에 구조 개선이 더 중요해지는 이유: 코드는 빨리 늘어나는데 **경계가 없으면 검증 단위도 없다.** 경계가 있어야 "이 부분만 테스트로 고정하고 이 부분만 바꾼다"가 가능하다.

### 4.1 세 가지 구조 패턴 (이름 붙이기)

| 하고 싶은 일 | 패턴 | 핵심 |
|---|---|---|
| 한 덩어리를 단위별로 떼어낸다 | **Strangler Fig (교살자 무화과)** | 새 것을 옛것 옆에서 키우며 기능 하나씩 라우팅을 옮긴다. 빅뱅 재작성의 위험을 피한다 (Fowler, 2004) |
| 낡은/외부 시스템의 의미가 새 설계를 오염시키지 않게 한다 | **Anti-Corruption Layer (완충·번역 계층)** | 경계에 facade/adapter를 두고 의미를 번역한다 (DDD, Evans) — "쿠션 서비스"와 같은 계열 |
| 흩어진 제어 로직의 진입점을 하나로 | **Facade / 단일 진입점** | 호출자는 하나만 알고, 내부 변경은 뒤에서 흡수 |

### 4.2 모듈러 모놀리스 vs 서비스 분리 — 용어를 정확히

| | 모듈러 모놀리스 | 서비스(프로세스) 분리 |
|---|---|---|
| 배포 단위 | **하나** (안에서 모듈 경계만 나눔) | **여러 개** (프로세스·배포 독립) |
| 얻는 것 | 경계 강제 + 단순한 운영 | 독립 배포·장애 격리·독립 확장 |
| 지불하는 것 | 같이 배포·같이 죽음 | 네트워크 실패·정합성·운영 복잡도 |
| 선택 기준 | 팀이 작고 경계가 아직 흔들릴 때 | 경계가 안정적이고 격리 이득이 분명할 때 |

> **용어 함정**: 둘은 반대 방향의 결정이다. 문서·면접에서 "모듈화했다"고 말할 때 **어느 쪽인지 한 문장으로 못 박지 않으면** 질문 하나에 무너진다. ([모듈성 이론](deep-modularity-theory.md): 경계의 근거는 변경 이유와 응집)

### 4.3 유지 — 한 번 바꾸고 끝이 아니다

```
① 현재 동작을 테스트로 고정 ──▶ ② 구조 변경 ──▶ ③ 정적 분석 CI로 기준 유지
   (변경의 안전벨트)             (분리·완충·통합)      (시간이 지나도 무너지지 않게)
```

③이 빠지면 구조는 6개월 뒤 원래대로 부식된다. 변경 경험과 **유지 경험**은 다른 능력이고, 시장이 시니어에게 묻는 건 후자다.
([품질 게이트·팀 코드 표준](../lang/java/quality-gates-and-standards.md): IDE → pre-commit → CI 3겹 강제와 ratchet)

## 5. 3단 요약 (암기)

- **① 결론 · WHAT** — AI로 구현 비용이 급락하면서 병목은 **검증**으로 옮겨갔다. 그래서 같은 수준에 머물지 않는 방법은 "더 많이 쓰기"가 아니라 **판별 전문성 + 테스트 구조**를 갖추고 도전 범위를 넓히는 것이다.
- **② 원리 · HOW** — 검증은 3층: 오라클(비교할 정답) → 고정 후 변경(현재 동작 박제) → 측정(주장과 증거 분리, 확인/미확인 구분 기록). AI 사용은 개인 요령이 아니라 **규칙 파일·프롬프트 방식·검증 절차를 문서로 고정**해 도구가 바뀌어도 품질이 유지되게 한다. 구조 변경은 **고정 → 변경 → CI로 유지** 순서다.
- **③ 확장 · TRADE-OFF** — 검증은 공짜가 아니다: 오라클이 없는 영역은 속성 테스트로 간접 검증할 수밖에 없고, 테스트 통과는 **스위트가 잡는 범위까지만** 보장한다(pgrust의 직렬 러너 지적). 구조 분리는 격리를 얻는 대신 네트워크·정합성·운영 비용을 낸다 — 모듈러 모놀리스와 서비스 분리는 **반대 방향의 결정**이라 용어부터 정확해야 한다.

## 용어 사전 (영 ↔ 한)

| 용어 | 뜻 |
|---|---|
| oracle | 오라클 — 결과를 대조할 신뢰된 정답(기존 스위트·구현) |
| regression test | 회귀 테스트 — 변경이 기존 동작을 깨지 않았는지 확인 |
| characterization test | 특성화 테스트 — 현재 동작을 있는 그대로 고정하는 테스트 |
| property-based testing | 속성 기반 테스트 — 불변식을 무작위 입력으로 검증 |
| benchmark validity | 벤치마크 타당성 — 조건·반복·분포 가정이 갖춰진 측정 |
| rule file | 규칙 파일 — AI에게 맥락·금기를 주는 문서 (예: CLAUDE.md) |
| strangler fig | 교살자 무화과 패턴 — 새 것을 옆에서 키워 점진 대체 |
| anti-corruption layer | 부패 방지 계층 — 경계에서 의미를 번역해 오염 차단 |
| facade | 파사드 — 복잡한 내부를 하나의 진입점 뒤에 숨김 |
| modular monolith | 모듈러 모놀리스 — 한 배포 단위 안의 모듈 경계 |
| quality gate / ratchet | 품질 관문 / 래칫 — 기준을 한 방향으로만 조여 가는 장치 |
